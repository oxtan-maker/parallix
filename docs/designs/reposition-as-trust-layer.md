# Design: Reposition Parallix as the trust layer, not another worktree orchestrator

## Problem Statement

Parallix is published, alpha, and technically complete enough to run a full mission
lifecycle. It has zero outside operators. The session established that this is not a
feature gap — it is a positioning gap. Parallix is marketed as an isolation product
("run several AI coding agents on one repo without clobbering each other") in a
category where isolation became free and commoditized in 2026.

## Demand Evidence

None outside the founder. Stage: "Only me." npm publication exists; no evidence any
external operator has completed a mission.

The README's "+57% to an order of magnitude" figure comes from an internal
retrospective — self-measured, and discounted to zero by any outside reader. It is a
motivation artifact, not demand evidence.

The one genuine asset: the founder runs Parallix daily on Parallix. Dogfooding a
workflow tool you depend on is the strongest possible pre-demand starting position.
The corresponding risk: every design decision so far has been optimized for exactly
one operator.

## Status Quo

Hand-rolled `git worktree` + tmux + ~20 lines of bash, written by the user themselves.

This is the hardest status quo to displace, not because it is good but because its
owner built it, can read all 20 lines, and trusts it. The switching cost is trust,
not features. Codex, cold: "Parallix must earn replacement trust, not win on
orchestration features. The product should make its decisions, state, failures, and
escape hatches more legible than that script."

## Landscape (web search, Sept 2026)

Git worktrees went load-bearing for AI coding around Q1 2026. The isolation category
is now crowded and free: Composio Agent Orchestrator, Emdash, Baton, Conductor
(conductor.build), Claude Squad, Crystal, Vibe Kanban, Agent Kanban, agentree,
CodeRabbit git-worktree-runner, worktree-cli.

Adoption research on orchestrators names the failure mode as trust and observability
— "teams either over-trust agents by letting them run unsupervised or under-trust
them by reviewing every line, defeating the purpose" — plus cost/ROI. Not isolation.

**Eureka:** the whole category builds isolation products; the documented reason the
category fails is trust. Parallix is the only tool found whose core mechanic is a
trust ladder — forced review by a preferentially-different agent family,
self-approval blocked at the provider, a repo-owned verification gate running the
operator's own command, Bubblewrap confinement, human-owned squash-merge. Parallix
built the answer to the failure mode and marketed it as an entry in the crowded
category.

## Target User

Agent-limit power user: burns usage caps daily, pays 2-3 providers, has runs stop
mid-task, babysits restarts, loses the thread. Failover + resumable `Next action:`
checkpoints is the headline for this person.

Not yet a named human. See Open Questions.

## Premises (agreed)

1. Worktree isolation is commodity. Parallix cannot win positioning there, and
   leading with it invites a bake-off against twelve free tools on its weakest axis.
2. The differentiator is the trust ladder: cross-family review, provider-blocked
   self-approval, repo-owned verification gate, sandbox, human-owned merge.
3. The buyer is the agent-limit power user who already hand-rolled worktrees.
   Switching cost is trust, not features. (Kept as stated over a cross-model
   challenge — see below.)
4. The blocker is zero outside operators, not a missing feature.
5'. **Revised.** Forgejo is opt-in and the workflow runs without it; the adoption
   tax is first-run and documentation, not architecture. The founder rejected the
   stronger claim that local-first + Forgejo is architecturally an adoption blocker,
   and the README supports the rejection. What remains: `px setup`'s Forgejo
   bootstrap is prominent enough that a stranger may believe it is required.

## Cross-Model Perspective (Codex, cold read)

- **Steelman:** "Parallix is a local control plane for delegating coding work without
  delegating judgment: agents can work concurrently, but changes pass through
  independent review, repo-defined verification, and a human merge decision. Its
  value is trustworthy throughput under unreliable, rate-limited agents — not
  worktrees." Reached premise 2 independently, without the landscape search.
- **Most revealing answer:** "Devs already wrote ~20 lines of bash they trust."
- **Challenged premise 3:** "'agent-limit power user' is a hypothesis, not a buyer,
  until it names real people with a repeated pain." Proposed bar: five operators
  independently install, complete a mission, and return a second week without founder
  help. Founder kept premise 3 as stated.
- **Proposed prototype:** a zero-config `px run` / `px review` / `px status` /
  `px resume` CLI, skipping Forgejo, sandboxing, failover, Backlog.md, dashboards.
  Assessed as a smaller rebuild of what already ships and exists tested — rejected on
  that basis.

## Approaches Considered

### Approach A: Reposition, don't rebuild — CHOSEN
No new subsystems. README and npm page lead with the trust ladder; the no-Forgejo
path becomes the documented default; one 60-second proof-of-value demo ending in
"reviewed by a different agent family, your gate passed, you decide."
Effort S (human ~3 days / CC ~2 hours). Risk Low. Reuses everything.

### Approach B: Zero-config wedge — not chosen
A no-config first-run path (`px run` facade over the existing lifecycle), everything
else behind `px setup`. Rejected for now: it bets that first-run friction rather than
positioning is the blocker, and that bet costs weeks before it can be tested. A is
the cheaper experiment against the same hypothesis.

### Approach C: Standalone `px review` as a drop-in for other orchestrators — not chosen
Point `px review` at any branch or worktree that any tool produced, run the
cross-family review + gate + verdict, making competing orchestrators a distribution
channel rather than rivals. Rejected for now on sequencing, not merit: it is the
strongest strategic move if the trust pitch lands, and it should be reconsidered the
moment A produces evidence. Blocking unknown: how tightly `px review` is coupled to
Parallix-created mission state.

## Recommended Approach

**A only.** The cheapest experiment that can kill the hypothesis. If the trust pitch
does not pull anyone, three days were spent instead of three weeks — and B and C both
become better-informed. If it does pull, C is the follow-on.

Scope of A:
1. README first three lines and npm description lead with the trust ladder, not
   parallel isolation.
2. Demote the "+57% to order of magnitude" figure or label it explicitly as an
   internal self-measurement.
3. Make the no-Forgejo path the documented default path; move `px setup` Forgejo
   bootstrap into the optional-integrations section only.
4. One 60-second first-run demo whose final line is a review verdict from a
   different agent family plus a gate result.
5. Legibility pass on what a first-run operator can inspect: plain files, one
   readable event log, no hidden scheduler state (Codex's point — the bash script's
   superpower is that its owner can read all of it).

## Open Questions

- No named human for the target archetype. This is the largest unresolved item; the
  assignment addresses it directly.
- Is `px review` runnable against an externally-created branch? Decides whether
  Approach C is a docs change or a real refactor. Not resolved this session.
- No CI/release automation exists today; publishing is manual. Not a blocker for A,
  but it caps how fast a positioning fix reaches npm.

## Success Criteria

- 5 named operators who are not the founder have installed Parallix cold.
- At least 1 of them completed a full mission through `px integrate`.
- At least 1 watched, unassisted first run with the founder silent, and a written
  note of the first point of confusion.
- Kill criterion: if 5 people read the retitled pitch and none install, the trust
  positioning is wrong too, and the problem is upstream of both A and C.

## Distribution Plan

Already published to npm as `@magnusekdahl/parallix`; Approach A changes the pitch,
not the channel. The npm page and README *are* the distribution surface, which is
exactly why A is the highest-leverage cheap change. No CI/release automation today —
each repositioning edit requires a manual publish.

## The Assignment

Rewrite the first three lines of the README and the npm description to lead with the
trust ladder, publish it, then take it to five specific named people who run coding

Then screenshare with one of them while they install it cold. Say nothing. Do not

That single note is worth more than the next three weeks of code.
