When should an agent keep its context, compact it or start a fresh session?

Start fresh when a failing check or a moved main branch sets the next job: 43–46% less time and 46–70% less cost than continuing. When the agent continues its own plan, compact; fresh took up to 73% longer.

Cost means implementer tokens, including cache reads and compaction, priced at Claude Sonnet 5.5 API rates. Parallix uses discounted subscriptions and local AI; these figures compare usage, not its actual bill.

Magnus Ekdahl · 2 November 2026

In Parallix, one agent implements a change and another agent, using a different model, reviews it. Then it's time for human review, and integration checks run before anything lands. Each of those stages can send the work back. Each return creates another job, and the same choice comes up every time: keep the agent's conversation, compact it, or start a fresh session.

These are the context choices Parallix makes; the numbers match the diagram:

  1. Checkpoint. Part of the implementation is delivered. Compact and continue, keeping the important knowledge gathered so far.
  2. Failed check. Start a fresh session with the diagnostics and requirements.
  3. Act on review. The implementer addresses the findings. Compact before starting the fix. Continuing without compaction is another option.
  4. Rebase conflict. When main moves, start a fresh session with the current branch and the intent of the change. This can happen before review or integration.

Compact replaces earlier conversation with a summary and continues from there. It costs a summarisation call and can lose details. Fresh starts a new conversation with the task and current evidence; the agent has to recover anything else it needs from the repository. Continue carries the existing conversation forward, including its investigation and tool output. It is what you get when you run agents by hand without handling context: each keeps one session until the work is done, compacting only near the context limit.

This tradeoff also appears in the wider research. Anthropic's context engineering guide describes how compaction preserves continuity while risking the loss of useful detail. Its long-running agent experiments show why new sessions need written progress and Git history. In JetBrains' SWE-agent experiments, summaries sometimes led to longer runs despite reducing the context. These explain the costs to look for; the Parallix replays ask which choice pays at each point in the workflow.

When main moves, adapt the work to main's changes

A rebase asks the agent to reconcile the task's change with changes in the main branch that have happened in the middle of the task. This is expected if you are running multiple tasks in parallel. The results and monthly estimate count only rebases that needed conflict resolution.

When a check fails

When code comes back from a failed check such as a test, Parallix gives the implementer the failing command, its output and the original requirements, and the current branch with the changes from the last round; the new job is to find the cause of the failure and repair it.

Across eleven tasks, Fresh's cost was 46% lower than Continue and 41% lower than Compact through independent approval. Recorded time was 43% lower than Continue and 37% lower than Compact. It cost less in all eleven comparisons with Continue and ten with Compact. One sample was hit by an error in the experiment setup and was excluded.

Acting on review findings

When a reviewer sends work back, the agent has to fix the problem and preserve the parts that already work.

Compact's cost was 25% lower than Continue and 13% lower than Fresh, and it was cheaper than Continue with both models. Fresh cost 15% less than Continue, despite taking longer.

Fresh took 8% longer than Continue and 17% longer than Compact. Compact took 8% less time than Continue in total. Compact was slower than Continue on the Claude tasks, but faster on the Qwen tasks. Parallix uses Compact here for now; more data is needed to establish whether the effect is significant.

Between checkpoints

A checkpoint is a partial delivery of the work, but the agent still needs to complete the remaining checkpoints.

Across twenty Qwen tasks, Compact took 8% less time than Continue. It was faster in twelve tasks and slower in eight. Its cost was 1% higher. I would keep Compact here for the shorter processing time and the continuity of a summary.

Compact used 3% fewer tokens than Continue but cost 1% more, because it sent 18% more uncached input, which is priced at twenty times a cache read. A likely reason, which these records don't isolate, is that a new summary can't reuse the cached prefix of the old conversation. Over the recorded month, I estimate about $6 more for checkpoint work and ten fewer agent processing hours. For Parallix development, I take that tradeoff since processing time is the current bottleneck.

Across the twenty tasks, Fresh took 73% longer than Compact and cost 57% more. Against Continue, it took 59% longer and cost 59% more. Compact was faster in eighteen tasks and cost less in seventeen. The total time and cost differences are statistically significant.4

What this means for Parallix

I reconstructed the usage records for the period 23 September to 23 October and applied the experiments' cost ratios at each decision point.5

My rule for Parallix is Compact between checkpoints and before review fixes, and Fresh after failed checks. The replays tested the choices Parallix already made: they supported three and changed one, rebases, which now start fresh. At checkpoints, I accept the small cost premium for the shorter recorded processing time.

For the recorded workload, I estimate about $450 less in cost than using Continue throughout, a 27% reduction, and about 100 h less agent processing time (25%). These processing hours are summed across concurrent tasks, not hours of my time or calendar time saved.6

Every comparison stops at agent approval; I did not measure what reaches human review. I will monitor review rounds, defects found after approval, and time spent at each stage. I would reverse a choice if extra repairs erase its time saving, more defects get through approval, or a change of model or workload removes the advantage. If usage caps become the bottleneck, I would reconsider paying more for Compact at checkpoints.

Choose context for the next job, and measure the cost of getting the work right.

Sources and method

Results checked on 2 November 2026.

1. Rebase results

Nine matched tasks, each run with all three tactics. Exact two-sided paired permutation tests of total cost and time give p = .0039 for Fresh versus Continue and .0078 for Fresh versus Compact, for both measures. All runs passed local validation; that does not establish equal code quality. ↩

2. Failed checks

Eleven matched tasks. Exact two-sided paired permutation tests of total cost and time give p = .00098 for Fresh versus Continue on both measures. Fresh versus Compact gives p = .00195 for cost and .00488 for time. ↩

3. Acting on review findings

12 tasks: seven used Qwen and five Claude; the model and reviewer stayed fixed within each task. Time includes all repairs, compaction, checks and review through approval, excluding setup and inactive waits. This captures extra review and validation caused by a tactic that makes more mistakes. Exact two-sided paired permutation tests of total cost and time give p = .273 and .709 for Compact versus Continue; neither establishes a certain difference. ↩

4. Checkpoint results

Twenty matched tasks, each run with all three tactics. Both measures include recorded compaction and stop before independent review. Exact two-sided paired permutation tests of total cost and time give: Compact versus Fresh, p = .00325 for cost and .000042 for time; Compact versus Continue, p = .884 for cost and .549 for time. The results are exploratory. ↩

5. Cost comparison

Sonnet 5.5 prices per million tokens, checked 30 October: input $2, output $10, cache reads $0.10, five-minute writes $2.50 and one-hour writes $4. Official prices. Production tokens are assigned once to a workflow stage, priced, then scaled by matched experimental cost ratios. Dollar amounts are rounded by stage; percentages use unrounded estimates. Repair episodes include implementer work through approval. Drafting, reviewer and other constant work are excluded. Codex tokens with recovered input/output/cache categories are converted to the same Sonnet prices; missing histories remain unpriced. Stage attribution uses prompts and workflow records. Missing Codex histories and unlogged compaction usage prevent a complete monthly total. ↩

6. Monthly time estimate

Estimated work at the four decision points over 23 September–23 October, applying paired stage time ratios to recorded monthly durations. Concurrent tasks add work hours; these are not calendar delivery hours. ↩

How the comparisons were run

Each matched comparison starts from the same code and task. Tasks were selected from recoverable records in one repository, rather than sampled randomly. All reported p-values are unadjusted; the permutation tests use the sum of within-task differences. Continue can include earlier compaction; the larger studies also allowed automatic compaction near the context limit in every tactic. Token totals include cache reads and compaction calls, with reviewer tokens counted separately. These measure work, not a provider bill or electricity use.
