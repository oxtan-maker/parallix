Building a cheaper review loop for coding agents using Jev

When tests find a regression in agent-written code, the agent repairs it and the change needs another review. Jev, TypeSafe’s hosted classifier, clears about a third of those re-reviews in my personal workflow, at a fraction of the cost of a general LLM review.

Magnus Ekdahl · 21 October 2026

In Parallix, one agent family implements a change and another agent, using a different model, reviews it before I do. Human review and integration gates decide when the work is done. I don't expect the first agent to get it right first time; it usually needs a couple of feedback cycles.*

Each re-review used to mean another general LLM review. That needs the requirements and codebase context, more than Jev can fit in 32k input tokens per question. Many re-reviews are easier: did this repair fix the failed check without weakening it? And would it not be great if we can take decisions in those cases an order of magnitude faster and a couple of orders of magnitude cheaper?†

The result: 36% of re-reviews

Jev cleared 41 of 114 re-reviews (36%)‡: 37 repairs to local integration gates and four general re-reviews. That leaves 73 for the general reviewer. A typical integration-gate repair fixes one failed test or a performance regression.

Integration gates

Early experiments asked whether a repair addressed an integration failure. Jev kept leaving the decision to the general reviewer. Some requests also exceeded its token budget. Better packing got the requests through, but the decisions still weren’t useful.

The test run already answers whether the test passes after the fix. A reviewer has a different job. An agent can make a test pass by fixing a code or test regression, or by deleting or weakening a test. Both can produce a green exit status; only one preserves what the test was meant to establish.

That gave Jev a bounded job: judge whether the repair preserves the check and the behaviour already approved. The question names concrete ways to weaken a check, including skipping a test, loosening assertions or raising a CPU or time budget.

Build the evidence around that judgment

The classifier needs to know what was approved and what the repair changed. Its packet identifies the approved and repair revisions, supplies their relevant diff, names the failed check and states omissions. It excludes files changed only by other work landed on main and identifies changes brought in by a rebase. Rebase changes in the same file can still appear in the diff.

The local repair loop reruns its gates before re-review. A later rebase does not by itself require repeating every local test; upstream CI provides the usual integration validation. Jev’s approval leaves both stages in place.

The model version matters. I use Jev 1.13: on the same 43 approved historical repairs, it cleared 24 against Jev 1.14’s 12.

General re-reviews

A request for changes gives Jev a specific question: did the repair fix what the reviewer asked for? Parallix sends the earlier findings, repair diff, relevant source and implementer’s response. Three questions run in parallel over that evidence, covering the requested fixes and related regressions introduced by the repair.

One clear was a one-line TypeScript correction. A test helper accepted the wrong callback return type; the repair changed it to the type the test runner requires.

The panel can approve or send the patch back to the implementer. With uncertainty, conflicting votes or a failed call, the general reviewer takes over. This path cleared four re-reviews in the dataset.

An approval can miss a defect

Jev is a different model from general LLMs such as Claude and makes different decisions. It can make mistakes, but the difference I found in this sample was small.1 For example, in a local integration repair, the implementer added an admission property to a fixture that already had one. Jev cleared the change. The focused suite passed, but the separate TypeScript check later in the process rejected the duplicate key.

The Jev tradeoffs

For me, the main cost is the attention tied up in review: waiting, checking progress and switching back. The estimate saves about two hours of review work per month at 800 re-reviews. How much human attention that recovers depends on when the workflow needs me, and on how quickly I switch to the next task instead of waiting for the re-review to finish. Reviews that run unattended offer less direct benefit.

Parallix keeps a human in the loop on purpose; I cannot assume a single agent pass finishes a mission. A defect Jev misses can reach my review or fail a later gate.

Cost matters too. Re-review API spend also falls by about 35%: $74 a month at API prices, before extra repairs and upkeep. That can matter when reviews compete for a fixed token budget. Human approval and the required gates stay in place in both options:

What I’d carry to another team is the bounded question: give Jev a repair it can judge, leave uncertain cases with the general reviewer, and keep human approval and the downstream gates. Count the misses as well as the reviews avoided; the extra repair cycles determine whether the saving survives.

Research correction: an inactive classification path

I found a routing bug that left general re-review classification inactive for 42 of these rounds. I reran their original evidence with the existing questions, thresholds and pinned model: four approvals and 38 abstentions. Four control packets matched the recorded production hashes. Each approval agreed with the general reviewer at the same revision. These four rounds were already inside the 114, giving 37 integration-gate repair approvals plus four general re-review approvals. Jev requested no changes in this dataset; it has done so historically. The aggregate data retains the rerun cases, protocol and original workflow counts. The production routing fix is queued separately.

The three-question panel is not a majority vote. One approve vote with no reject can clear; one reject with no approve can return the repair. Conflicting votes, a failed call or no decisive vote leave the decision to the general reviewer. The v3 question can approve at a label score of 0.51; v1 needs 0.80. The v1 and original questions can reject at 0.89. Three of the four replay approvals scored 0.53–0.58; the fourth scored 0.71. These historically tuned scores are not calibrated probabilities of defect-free code. The exact questions and aggregation are in the question definitions and panel policy.

How often a review requested fixes

The historical baseline uses recorded pull-request review decisions from 14 August through 21 October, beginning with the first complete local calendar day after repairs to the review statistics. General reviewers requested changes in 449 of 1,242 rounds (36.2%): 197 of 456 first reviews (43.2%) and 252 of 786 re-reviews (32.1%). First reviews remain with the general reviewer; the matrix uses the re-review rate to match the work Jev replaces.

Each mission/round counts once, using its recorded decision. Where an older round lacks that decision, its latest recorded reviewer outcome supplies it: 172 rounds in total, including 78 re-reviews. Classifier decisions and mechanical approval restorations are excluded from this baseline. These are requests for changes, rather than independently verified defects.

The estimate subtracts the sample’s one confirmed miss per 114 re-reviews from 252/786: 32.1% − 0.9 percentage points = 31.2%. The four general re-review clears matched general approvals and leave the sample’s 18 returns unchanged. The case investigations establish one additional miss; they did not uniformly adjudicate every clear. This calculation holds the review mix and repair attempts fixed. Additional undiscovered misses would lower the combined rate. The historical general-reviewer cohort and current mixed-route sample are not matched populations.
