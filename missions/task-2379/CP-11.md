### F1 (fixed) — stale-`active` override recovery emitted out-of-order lane events

Recovery no longer lets the production handoff stamp the recovered
`active → review` transition with its own wall clock.
`recoverMissionForIntegration` derives the authoritative review-entry
timestamp — the Review round's own `startedAt`, or the PR creation time
(`getPrStatus` now surfaces `createdAt`) when recovery creates the Review —
and forwards it through `submitForReview` → `performHandoff` as an explicit
`occurredAt` (a genuine handoff passes nothing and keeps the wall clock).
Recovery stops with an actionable error when no authoritative entry
timestamp exists or when the entry postdates the approval, instead of
persisting an out-of-order lane event the projection silently drops.

- `test/integrate.test.ts` "R5: stale active recovery with human override persists a real ReviewerDecision, then chains existing operations" — the stub now mirrors the production contract (stamps the forwarded timestamp, wall clock when absent), so it stays red if recovery forgets to forward the entry time; it asserts `active → review .occurred_at = PR created_at` and `active → review .occurred_at <= review → integration .occurred_at`. Sensitivity verified this round: removing the `occurredAt` forwarding makes R5 red (mutation not committed).
- `test/integrate.test.ts` "R5b: override recovery stops without an authoritative review-entry timestamp" — missing entry data and inverted entry/approval data both abort before any handoff or transition runs.
- `test/integrate.test.ts` "R4: stale active recovery chains submit-for-review then approve with original decidedAt" — asserts the recovered `active → review` carries the Review round's `startedAt`.
- `npm test -- test/integrate.test.ts`

### F2 (fixed) — superseded default-user approval persisted as authoritative

`getLatestReviewDecision` now treats the default-user approval as an
override only while that user's own latest non-dismissed formal review is
`APPROVED`; a later `REQUEST_CHANGES` by the same login supersedes it. A
`REQUEST_CHANGES` by a different user does not (existing tests unchanged).

- `test/forgejo.test.ts` "getLatestReviewDecision ignores a default-user approval superseded by the same user's later REQUEST_CHANGES"
- `npm test -- test/forgejo.test.ts`

### F3 (fixed) — `--dry-run` preflight failed for the case the real run accepts

New pure `recoveryEstablishesApproval(context)` predicts the authority the
real run would establish through recovery. The real run persists it; the
dry run (which skips recovery) consumes the same prediction in
`evaluateTaskStatusForIntegration` and the Forgejo-approval preflight branch,
so `--dry-run` reports "recovery would establish the authoritative
approval" instead of failing `task-status` / `pr-approval` for the
override case.

- `test/integrate.test.ts` "F3: dry-run preflight accepts the override case the real run accepts" — override context passes both checks and prints the would-be-recorded authority; the no-override control still fails both.
- `npm test -- test/integrate.test.ts`

### F4 (parked) — out-of-scope `worktree.ts` + `package-lock.json` changes

Parked as `backlog/tasks/task-2382 - Split out-of-scope worktree and lock changes from task-2379.md` (TASK-2382, status backlog). Both changes stay on the branch in this round because this checkout's git dir is named `.git-worktree` (the read-only-host repair documented in CP 10): reverting the `resolveWorktree` normalization makes `resolveWorktree` hand the git dir itself to the rebase workflow, which would break this branch's own ability to run its verification gates. TASK-2382 carries the split/justify requirement plus the revert-hazard note.
