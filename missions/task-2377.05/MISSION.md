# Mission: Migrate CLI and handoff bounces to the rebound kernel (task-2377.05)

## Goal
Move the last standalone agent-bounce paths onto the rebound kernel (`src/application/rebound-kernel.ts`): the `px rebase` hook-failure auto-bounce and its `rebase --continue` retry loops in `src/application/rebase-workflow.ts`, the `px integrate` squash-commit hook bounce in `src/adapters/cli/commands/integrate.ts`, and the two `px active` handoff relaunch loops in `src/adapters/cli/commands/active.ts` (checkpoint-validation repair and handoff-failure repair). Each becomes a `rebound()` call with a `verify` callback that re-runs the exact check that failed — `rebase --continue`, the squash commit, checkpoint re-validation, and a re-run of `performHandoff` respectively — so no bounce is reported as fixed without a passing re-run. With those consumers migrated, delete the superseded standalone bounce policy `handleHookFailureAutoBounce` / `MAX_HOOK_RETRY` and its `hookFailureRetryCount` review-state metadata counter from `src/application/hook-failure-workflow.ts` (keeping `classifyHookFailure` as the hook detector), and lock the resulting invariant with an allow-list test: no code path launches an agent to fix a failure except through the kernel.

## Why Now
TASK-2377.03 shipped the kernel and wired the two pre-review incident paths; TASK-2377.04 migrated the review-loop artifact bounces and deleted the persisted retry counters from review state and `mission_reviews`. What remains is exactly this mission's surface, and it is the part that still contradicts the kernel's two invariants. `handleHookFailureAutoBounce` in `src/application/hook-failure-workflow.ts` still writes a cumulative `hookFailureRetryCount` into review-state metadata — the last persisted retry counter in the codebase, and the same split-brain shape (two processes, one counter) that the kernel abandoned after task-2369.13. It also still reports success on a non-zero-status-free launch without re-running the hook, and its callers rebuild their own retry loops around it: `src/application/rebase-workflow.ts` has one bounce-and-retry loop after the initial rebase plus a `recoverHookFailureFromContinue` helper invoked at four separate `rebase --continue` sites, and `src/adapters/cli/commands/integrate.ts` has its own `while (commitResult.status !== 0)` bounce loop. The `px active` handoff paths in `src/adapters/cli/commands/active.ts` carry two more hand-rolled `maxCheckpointRelaunches = 2` / `maxRelaunches = 2` loops with their own classification calls. Five loops, three retry-budget implementations, one persisted counter, for one policy. Landing this leaves the kernel as the single bounce path, so the next failure mode costs one reason variant, one classifier rule, and one verify callback instead of a sixth loop. TASK-2372 already deleted the duplicate integrate implementation (`src/adapters/cli/commands/integrate-command.ts` is gone; `src/application/integrate-command-use-case.ts` is the live board-publishing use case, not a copy), so this mission's dead-code obligation is a verification, not a deletion.

## Scope
- **`px rebase` hook bounces → kernel.** In `src/application/rebase-workflow.ts`, replace every `handleHookFailureAutoBounce` / `bounceHookFailure` call and the retry loops built around it with `rebound({ kind: 'hook-failure', hook, operation: 'rebase --continue', output }, context)` whose `verify` callback runs `git add -A` followed by `rebase --continue` (the same commands the current loops run) and returns `ok` when that exits 0 or reports "already up to date". This covers the post-initial-rebase bounce loop and the `recoverHookFailureFromContinue` helper at all four `--continue` call sites; `recoverHookFailureFromContinue` collapses to a single kernel call. Outcomes map: `fixed` → continue the existing success path; `exhausted` / `human-only` → the existing stranded path with the kernel's last diagnostic and the existing recovery hint.
- **`px integrate` squash-commit hook bounce → kernel.** In `src/adapters/cli/commands/integrate.ts`, replace the `while (commitResult.status !== 0)` bounce loop's `handleHookFailureAutoBounce` call with `rebound({ kind: 'hook-failure', hook, operation: 'squash commit', output }, context)` whose `verify` re-runs the same `git commit --only -m … -- <intendedPayloadPaths>` invocation. The `isIntendedPayloadAtHead` already-landed short-circuit, the non-hook-failure branch, and the `IntegrationAbort` stranded path are preserved. `src/adapters/cli/commands/integrate-post.ts`'s `handleHookFailureAutoBounce` wrapper is deleted with its policy; the port-assembly seams it provided (`startAgentFn`, `transitionTaskFn`, `applyAgentFallbackFn`, `selectAgentFn`, `workflowLauncherStatusFn`) are re-provided as the kernel context's `startAgent` / `transitionToImplementer` / `applyAgentFallback` injections so integrate tests keep a mock seam.
- **Handoff checkpoint-validation relaunch → kernel.** In `runHandoffAndReview` in `src/adapters/cli/commands/active.ts`, replace the `maxCheckpointRelaunches = 2` while-loop with `rebound({ kind: 'handoff-verification', error: validation.error }, context)` whose `verify` re-runs `validateCheckpointsBeforeHandoffFn(slug, worktree, …)`. The relaunchability decision stays where it is today (`validation.nextCheckpoint` or an `IncompleteEvidence` classification) as the guard that decides whether to call the kernel at all; non-relaunchable checkpoint errors keep emitting `checkpointValidationNextAction` and returning false, as does an `exhausted` / `human-only` outcome.
- **Handoff-failure relaunch → kernel.** Replace the `maxRelaunches = 2` while-loop with `rebound({ kind: 'handoff-verification', error: handoffResult.error, gateOutput: handoffResult.gateOutput }, context)` whose `verify` re-runs `_performHandoff(slug, { forgejoUser: agent, worktree, force: true })` and returns `ok` on `handoffResult.ok`, carrying the refreshed `handoffResult` forward so the gatekeeper-pushback and review-loop branches below see the post-verify result. The existing relaunchable guard (`dispatchAction !== 'HumanOnly' && failureClass !== 'GitBlockers'`) stays; the non-relaunchable branch — `repairHandoffFn` git-only repair, then its `isRelaunchableError` fallback relaunch — keeps its current shape, with that fallback relaunch also routed through the kernel with the same `performHandoff` verify.
- **Delete the superseded standalone policy.** Remove `handleHookFailureAutoBounce`, `MAX_HOOK_RETRY`, the `HookRebouncePort` type, and the `hookFailureRetryCount` metadata read/write from `src/application/hook-failure-workflow.ts`, leaving `classifyHookFailure` (still the hook detector that decides whether a Git failure is a hook failure at all). Remove the now-dangling re-exports and wrappers in `src/application/rebase-workflow.ts`, `src/application/ports/rebase-workflow.ts`, `src/adapters/rebase/rebase-workflow-adapter.ts`, `src/adapters/review/rebase.ts`, `src/adapters/cli/commands/rebase.ts`, `src/adapters/cli/commands/integrate.ts`, and `src/adapters/cli/commands/integrate-post.ts`.
- **`attemptAgentRelaunch` in `active.ts` — deleted (amendment A2).** Once both handoff loops call the kernel, `attemptAgentRelaunch` is deleted. What is genuinely launcher-side — the `workflowLauncherStatus` availability check and the resume-aware `startAgent` call — becomes a local `reboundLaunchPort` adapter that the kernel drives and that decides nothing; the relaunchability decision and the retry budget move to the kernel, and the gate-output content stays reachable through the kernel's `handoff-verification` prompt slots. `runHandoffAndReview` takes `startAgentFn` and `workflowLauncherStatusFn` as its injected seams in place of `attemptAgentRelaunchFn`. ## Authorized Amendments

Both amendments were requested by the operator during execution, after the
original contract was shown to conflict with how the product should behave. They
are recorded here so the tree and this document agree; the checkpoints carry the
full rationale and evidence.

- **A1 — a declared checkpoint gap is agent hallucination, not infrastructure.**
  Wiring the checkpoint-validation bounce exposed a classifier bug:
  `"Declared checkpoint documents are missing before handoff: CP-N…"` matched no
  rule and fell to the catch-all `InfraBlocker` / `HumanOnly` default, so the
  kernel refused to bounce and the mission stranded on manual instructions —
  even though one relaunch naming the gap is exactly the repair. ADR 0048 class 4
  already prescribed auto-send-back; only the pattern list was missing it. This
  lifts the read-only restriction on
  `src/application/failure-classification.ts` for one added rule. Recorded in
  CP-3 and CP-5.
- **A2 — `attemptAgentRelaunch` is deleted, not kept as an exception.** The
  original scope allowed keeping it as the kernel's launch port. Keeping it left
  a failure-repair launch outside the kernel (the gatekeeper-pushback
  remediation), which AC #3 would then hold only by documented exception rather
  than literally. The operator chose deletion, which extends scope to migrating
  that remediation. Its recursion bound and launch counts are preserved.
  Recorded in CP-3, CP-4, and CP-5.
