# Mission: Expose supported implementer options in `px --help` (task-2210)

## Goal
Make `px --help` an accurate, actionable entry point for selecting an implementer by exposing the supported implementer-setting options for the `draft` and `active` workflows, without changing either workflow's execution behavior.

## Why Now
The CLI already supports implementer selection in workflow commands, but people starting from `px --help` cannot discover that capability. This causes users and agents to use incomplete command guidance and makes workflow configuration appear unavailable.

## Refinement Signals
- Predicted NEL bucket: Small (0–80)
- Confidence: High
- Selection note: activate as-is
- Main drivers: help-output completeness for existing `draft` and `active` implementer configuration; focused command-help coverage; no lifecycle behavior change

## Scope
- Identify the command-help generation path for `px`, `px draft`, and `px active`, and compare it with the options each workflow already accepts.
- Add help text that makes the supported implementer-setting option discoverable from `px --help` and accurately directs users to the relevant `draft` and `active` command usage.
- Ensure the displayed option spelling, value form, defaults, and command applicability match the existing parser and workflow behavior.
- Add or update automated coverage for the relevant `px --help` output and the `draft`/`active` implementer option descriptions.
- Update user-facing CLI documentation only where the existing help contract or command reference needs to reflect the corrected discoverability.

## Out of Scope
- Changing how `draft` or `active` chooses, validates, persists, or invokes an implementer.
- Adding new command-line options, new implementer types, or configuration sources.
- Reworking unrelated `px` help formatting, command names, or documentation.
- Running a review, execution, or integration workflow as part of this mission.

## Success Criteria
> **Falsifiability rule (ADR 0039 Part 2):** Each criterion must be falsifiable. Forbidden: subjective adjectives ("easy, fast, simple, intuitive, user-friendly, responsive, quick, efficient" without an attached metric) and vague quantifiers ("multiple, several, some, many, few, various"). For refactor / condense / migration missions, the criterion must enumerate the specific elements (rules, files, behaviours) that must survive — generic phrases like "preserve critical content" are not sufficient.

- `px --help` exposes a discoverable path to the existing implementer-setting capability for both the `draft` and `active` workflows.
- The help for `draft` and `active` documents the existing implementer option with the exact parser-supported spelling and value syntax; it does not advertise an unsupported flag, value, or default.
- Automated tests assert the corrected help contract, including the `draft` and `active` implementer guidance, and pass without focused (`.only`) or unannotated skipped tests.
- Existing `draft` and `active` implementer-selection behavior remains unchanged apart from the help/documentation surface.
- The final verification is recorded with `./scripts/verify-local.sh all` and the final checkpoint includes a `## Goal Check` table with evidence for every criterion.

## Risks and Assumptions
- Assumption: implementer selection is already parser-supported for both `draft` and `active`; this mission documents and exposes that existing capability rather than introducing it.
- Risk: top-level and subcommand help may be generated by different code paths, so a change that fixes `px draft --help` alone may leave `px --help` incomplete. Verify all three help surfaces.
- Risk: help text can drift from parser semantics. Derive wording, accepted values, and defaults from the actual command definitions and cover them in tests.
- Risk: shared help snapshots or command-reference docs may be affected; update only the assertions and documentation that define this help contract.
