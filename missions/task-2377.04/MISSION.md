# Mission: Migrate review-loop bounces to the rebound kernel and delete dual retry persistence (task-2377.04)

## Goal
Migrate the review loop's remaining bounce paths — reviewer/implementer artifact-failure recovery and reviewer/implementer poll/disposition-timeout recovery — onto the rebound kernel (`src/application/rebound-kernel.ts`, from TASK-2377.03) so that every review-loop agent relaunch is verify-gated (`fixed` only when the failing check re-runs and passes), bound the total within-round relaunch fan-out with a per-round cap, and delete the now-obsolete persisted retry state: the review-state.json metadata retry counters and their keys, the `mission_reviews` SQLite retry columns (new drop migration), the review-state mapping sync for those fields, and the orphaned domain record methods.

## Why Now
TASK-2377.03 shipped the kernel and wired the two incident paths (pre-review gate, pre-review Git hook). The kernel contract explicitly names the remaining consumers as this mission: artifact-incomplete and agent-timeout reasons exist in the type union but have no real consumers, and the review loop still runs its own inline retry loops for artifact failures (`dispatchArtifactFailure` persisted metadata counter, `MAX_ARTIFACT_RETRY = 2`) and poll timeouts (`state.reviewerRetryCount` / `state.implementerRetryCount` while-loops capped at 2) that relaunch and re-poll but never re-run the failing check — "implementer relaunched" remains an unverified claim on exactly those paths. At the same time the persisted retry state (review-state metadata fields + keys, `mission_reviews.gate_failure_retry_count` / `hook_failure_retry_count` from migrations 0009/0012) encodes the cumulative-budget semantics the kernel abandoned after the task-2369.13 split-brain incident: the kernel budget is per local failure, in-memory, and persists nothing. Keeping both means two sources of truth for one fact, with the persisted counters still steering loop behavior even though they are no longer the kernel's budget. Deleting them completes the persistence half of the ADR 0053 authority boundary for review state; TASK-2377.05 then covers CLI/handoff bounces.

## Scope
- **Artifact bounces → kernel.** The reviewer artifact-failure path and the implementer artifact-failure path in `src/adapters/review/review-loop.ts` each become a `rebound({ kind: 'artifact-incomplete', role, diagnostic }, context)` call whose `verify` callback re-consumes the role's artifacts (`consumeReviewerArtifacts` / `consumeImplementerArtifacts`); `fixed` only when the re-consumed artifacts are complete and ok. `dispatchArtifactFailure` in `src/adapters/review/review-artifacts.ts` is rewritten to the kernel occurrence budget; the `REVIEWER_ARTIFACT_RETRY_KEY` / `IMPLEMENTER_ARTIFACT_RETRY_KEY` metadata counter read/write in it is deleted.
- **Poll/disposition timeouts → kernel.** The reviewer review-poll timeout and the implementer disposition-timeout recovery relaunches become `rebound({ kind: 'agent-timeout', role, diagnostic }, context)` calls whose `verify` callback re-polls with the recovery prompt's expectations (`pollForReview` for the reviewer, `pollForDisposition` for the implementer); `fixed` only when the re-poll returns a non-timeout result. The existing recovery prompts' context-compaction expectations are preserved via the kernel's single prompt builder.
- **Per-round relaunch cap.** An in-memory, per-review-round counter bounds total agent relaunches in a round (every launch attempt consumed by `rebound()` calls in that round, across reviewer retries, implementer retries, artifact/timeout bounces, and gate/hook bounces). Named exported default `DEFAULT_REBOUNDS_PER_ROUND = 6`, injectable through `startReviewLoop` options. Before each `rebound()` call the per-occurrence `maxAttempts` is clamped to the remaining round budget; when the round budget is exhausted the loop stops with an explicit diagnostic (log line plus a new named escalation reason) and performs no further relaunches; the counter resets when the next round starts. The round cap is in-memory only — it persists nothing.
- **Delete persisted retry state.**
  - `src/adapters/review/review-state.ts`: remove the `gateFailureRetryCount`, `hookFailureRetryCount`, `reviewerRetryCount`, `implementerRetryCount` fields and the `reviewerArtifactRetryCount` / `implementerArtifactRetryCount` metadata keys, plus their reset/serialize logic.
  - `src/adapters/review/review-state-mapping.ts`: remove the sync for the removed fields; remaining round fields keep round-tripping.
  - `src/domain/review.ts`: remove `gateFailureRetryCount` / `hookFailureRetryCount` and `recordGateFailureRetry` / `recordHookFailureRetry`; `recordReviewRetry` is orphaned by this migration (its only production callers were the removed per-occurrence retry loops) and is removed the same way, with `test/domain-review-workflow-state.test.ts` updated.
  - SQLite: one new forward-only drop migration (next free id after `0015-current-work-latest-per-mission.sql`) dropping `mission_reviews.gate_failure_retry_count` and `mission_reviews.hook_failure_retry_count`; `src/adapters/sqlite/mission-store.ts`, `src/adapters/sqlite/mission-serialization.ts`, `src/adapters/sqlite/mission-import-parsing.ts`, and `src/adapters/backlog/concrete-review-read-adapter.ts` stop reading/writing the removed columns and fields.
  - `src/adapters/review/review-commands.ts`: remove the status log lines that read the removed state fields.
  - Verify no copied hook regex or human-only override rule remains in the review-loop gate-handling code (expected: none remain after TASK-2377.03; if one is found it is deleted — the kernel's classifier replaces it).
- **Tests.** Expectation updates in `test/review-artifact-dispatcher.test.ts`, `test/review-artifacts.test.ts`, `test/task-1268-pre-review-gate-per-round.test.ts`, `test/task-1383-active-gate-failure-prompt.test.ts` (documented per criterion); new mock-only tests for the per-round cap, for a fresh per-occurrence budget after an exhausted occurrence, and for the drop migration. All tests fast, mocked, no real agents/git/Forgejo.
- **Docs.** Update the "Pre-review bounce policy" section in `docs/agents.md`: artifact/timeout bounces are now verify-gated like gate/hook bounces, no persisted retry counter remains, and the per-round relaunch cap exists.

Falsifiable by code search (`git grep startAgentFn src/adapters/review/review-loop.ts src/adapters/review/review-artifacts.ts` showing only the two first-launch sites) plus a mock-only test asserting a bounce relaunch occurs through the kernel-injected launch port.
- SC2 (artifact bounces verify-gated): Each `artifact-incomplete` rebound call passes a `verify` callback that re-consumes the role's artifacts; the outcome `fixed` is returned only when that re-consumption returns consumed-and-ok artifacts. A failing re-consumption consumes an attempt and relaunches with the fresh diagnostic; spent budget strands with the last diagnostic. Mock-only tests assert: re-consume fail → relaunch with fresh diagnostic; re-consume pass → `fixed` with the disposition; two failed re-consumes (default budget) → exhausted, no third launch.
- SC3 (timeout bounces verify-gated): Each `agent-timeout` rebound call passes a `verify` callback that re-polls with the recovery prompt's expectations (`pollForReview` for the reviewer, `pollForDisposition` for the implementer); `fixed` only when the re-poll returns a non-timeout result. Mock-only tests assert the same shape as SC2 for the timeout paths.
- SC4 (per-round cap): A named exported constant `DEFAULT_REBOUNDS_PER_ROUND` (default 6, injectable) bounds total bounce launch attempts per review round. A round that reaches the cap stops with an explicit diagnostic (log line plus a new named escalation reason) and performs no further relaunches; the next round starts with a fresh counter. Mock-only tests assert: a round hitting the cap stops with the diagnostic and exactly the capped number of launches; a round under the cap is unaffected; the counter resets per round.
- SC5 (review-state deleted): `gateFailureRetryCount`, `hookFailureRetryCount`, `reviewerRetryCount`, `implementerRetryCount` fields and the `reviewerArtifactRetryCount` / `implementerArtifactRetryCount` metadata keys no longer exist in `src/adapters/review/review-state.ts` or `src/adapters/review/review-state-mapping.ts`; `git grep` over `src/` returns zero remaining references outside the new migration file.

## Risks and Assumptions
- Dependency satisfied at draft: TASK-2377.03 is integrated on this branch's base (commit `6c912029d`; `src/application/rebound-kernel.ts` and `test/task-2377.03-rebound-kernel.test.ts` present). If the kernel module or its reason union is missing at execution start, stop (see Stop Rules).
- `DEFAULT_REBOUNDS_PER_ROUND = 6` is a deliberate policy choice: it tolerates legitimate single-round recovery (e.g. one artifact bounce + one timeout bounce + one gate/hook bounce at the default 2 attempts each) while bounding the fan-out that per-occurrence budgets alone allow. If the four named suites prove 6 too tight for a legitimate recovery, raise it (never lower it) and document the new value and rationale in the checkpoint; if no defensible value is clear, stop.
- Strand timing changes by design: the old cumulative persisted counters could strand a second occurrence of the same failure; the kernel's per-occurrence budget starts fresh each occurrence (SC7). Log/UX wording that references cumulative retry counts must be updated so output stays truthful; silent deletion of such wording is not.
- Expectation churn is expected in the four named suites: they encode the old behavior (persisted counters, relaunch-without-reverify, prompt wording). Every changed expectation is documented in the checkpoint with the test name and a one-line justification; silently deleting assertions is not.
- The `mission_review_rounds` columns `reviewer_retry_count` / `implementer_retry_count` (migration 0008) survive this mission: the state fields they were sourced from are removed, so new rounds store 0 and historical values round-trip unchanged. ADR 0053's description of retry counters as round columns stays true. If the implementer concludes the domain round fields must also be deleted for a coherent end state, stop and flag — that is a schema change beyond this description.
- The stale BLOCKED/PARKED disposition-recovery path is preserved as-is; if CP work shows it shares a launch path with a migrated bounce, stop and flag rather than migrating it (the description defers that to the checkpoint).
- Forward-only migrations: the runner checksums applied migrations and takes a pre-migration backup for irreversible ones; the drop migration must not edit 0009/0012.
- Tests stay mock-only and fast per repo test policy: `startAgent`, `verify`, polling, and the state store are injected; no real agents, git, or Forgejo.
