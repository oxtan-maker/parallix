# Mission: Integrate draft:create as a typed board capability without browser argv (task-2427)

## Goal
Make `draft:create` executable through the shared `BoardCommandController` board command boundary by reusing the existing application-owned draft workflow (`DraftCommandUseCase` + `DraftWorkflowPort`, the exact 9-step sequence `px draft` runs), exposed to the board through a narrow typed request that carries only the mission slug — never argv arrays, options bags, environment values, filesystem/worktree paths, or agent-launch options. The board's draft dispatch must be composed from a trusted, composition-built draft adapter (throwing exit function, progress-sink logging, composition-owned `missionServicesFn`), so duplicate-worktree, preflight, and lifecycle failures surface as typed `failure`/`rejected` outcomes and are never projected as a successful move. `draft:create` moves from `UNAVAILABLE_CAPABILITIES` into `INTEGRATED_CAPABILITIES` with availability derived from authoritative workflow eligibility; the CLI `px draft` behavior stays byte-identical.

## Why Now
TASK-2426 (done) made board capability availability truthful per controller instance: `BoardCommandController.canExecute` is the application-owned query, and production composition (`composeProductionCapabilities` in `src/composition/production-capabilities.ts`) now supplies the existing Mission services whenever Mission authority is available. `draft:create` was explicitly left in `UNAVAILABLE_CAPABILITIES` ("Draft is not available from the board") as the next bounded extraction. The local web board roadmap (ADR 0054, tasks 2430–2437: typed JSON-safe transport, loopback web host, authenticated typed mutation endpoint) will dispatch board actions from a browser, so every kind it can reach must already accept only checked domain values at the boundary. Draft is the lowest-risk remaining kind to integrate because its use case is already application-owned and port-based — the `DraftCommandUseCase` in `src/application/draft-command-use-case.ts` sequences all 9 steps through `DraftWorkflowPort` and already publishes current-work facts; the gap is purely that its entry point still accepts `string[]`/`Record<string, unknown>` (argv/options) and that the board boundary has no typed path into it.

## Risks and Assumptions
- **Assumption — adapter reusability:** `createDraftWorkflowAdapter(deps)` already merges injected deps over its CLI defaults (`exitFn`, `logFn`, `errorFn`, `missionServicesFn`, and the `*Fn` overrides in `preflight`), so the trusted composition adapter can be built by injecting a throwing `exitFn` and progress-sink loggers without touching the CLI adapter. If a workflow step bypasses `exitFn` and calls `process.exit` directly, the board path would kill the host process — stop (see Stop rules) rather than patch the adapter to swallow it.
- **Risk — exitFn contract:** the CLI adapter treats "exited" as a normal return (exited context), while the board needs aborts as typed outcomes; the mapping (thrown error ⇒ `failure`/`rejected`, including the use case's catch path that publishes `blocked`) must be verified by SC4's test, not assumed.
- **Risk — test-matrix churn:** moving `draft:create` between the two registries breaks four existing suites that assert the old matrix (`board-controller.test.ts` lines 64–71/215/229, `tui-action-bar.test.ts`, `task-2426-repro.test.ts` line 80, `tui-command-flow.test.ts`). Mitigated by SC8: update assertions to the new matrix, keep every other behavior assertion intact.
- **Risk — long-running dispatch:** draft launches an agent that runs for minutes/hours; the board dispatch must stay fire-and-forget with current-work publication (existing use case behavior) and unit tests must never launch a real agent (mocked ports only, per the unit-test budget).
- **Assumption — eligibility predicate:** the pre-draft state is `mission.status === 'backlog'` for open missions (missions are created by draft's intake step, so any already-drafted mission has an existing worktree/branch and a post-draft status). The dispatch backstop (existing worktree ⇒ failure, never success) covers projection/state drift; if the predicate proves wrong against real lifecycle facts, fix the predicate in the projection, not in the dispatch.
- **Risk — web-client expectation drift:** ADR 0054's mutation endpoint will dispatch `draft:create` through this same boundary; keeping the request slug-only now prevents a later retrofit that would accept richer payloads.

## Stop Rules
- Stop if reusing the current draft application policy requires a large refactor of the CLI argv flow (`runDraftCommand`/`createDraftWorkflowAdapter` preflight internals) — per the mission guardrail, keep `draft:create` unavailable, leave the registry as-is, and create a narrowly scoped follow-up instead of inventing a second draft path.
- Stop if making the board dispatch work would require spawning `px draft` as a subprocess or accepting/parsing a command string server-side.
- Stop if any draft workflow step bypasses the injectable `exitFn` (direct `process.exit`) such that a board-path abort would kill the host process — fix the boundary, not the workflow.
- Stop if any test would need real Forgejo, a real agent launch, or the operator's live SQLite database — use mocked ports and isolated temp fixtures only (unit tests stay fast).
- Stop if the draft availability predicate cannot be derived from existing authoritative facts (mission status/lane) without inventing new state.
- Stop if any behavior change to `active:execute`, `mission:intake`, `checkpoint:record`, or `handoff:record` (outcomes, cancellation, stale guard) is required to make `draft:create` work — that is a second mission.
