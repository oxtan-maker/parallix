## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-2332.08 removed the blanket adapters-to-adapters edge from `allowedDependencyGraph` and replaced it with `adapterPackageDependencies`, a table naming which sibling packages each adapter package may import. That closed the "any adapter may reach any adapter" hole, but the table's entries were transcribed from the edges the tree already had. Some are very wide — `cli` names 13 sibling packages, `rebase` and `review` name 9 and 8.

So the table is a ratchet, not a design: it prevents a *new* unnamed edge from appearing silently, but it certifies nothing about whether today's cross-adapter graph is correct. Several of those edges are the concrete symptom of adapters calling other adapters directly where the parent ADR intends an application-owned port supplied by composition.

This task narrows the table toward the intended shape: route the edges that represent behaviour (rather than a shared host mechanism) through ports under `src/application/ports/`, implemented by adapters and wired in `src/composition/`. It is deliberately scoped to dependency direction and does not change product-facing CLI behaviour.

Depends on TASK-2332.16 because the workflow-ownership decision made there determines which cross-adapter edges are legitimate mechanism use and which are workflow sequencing that must move out of the adapter layer altogether.
<!-- SECTION:DESCRIPTION:END -->
