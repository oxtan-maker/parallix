## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
After dependency and suite ownership are known, evaluate optional selective result reuse with existing task tooling, not a custom dependency-analysis/cache engine. Preserve exact-candidate certification, fresh external checks, all mandatory side effects, and performance/liveness guards. Include transitive runner/bootstrap imports, runtime resources, environment, toolchain, mocks, generated inputs and lockfile; conservatively invalidate unknown dependencies.

A narrow target must not restore cached whole-repository zero-hit coverage under an incomplete key. Reuse only accurately scoped fragments and combine them with current source inventory/denominator and current candidate executions. Validate edits outside a slice, common helpers, dynamic imports, fixture assets and environment. Nx prior exact-input hits are not representative changed-candidate savings. This is conditional research: a reject decision completes the evaluation; do not force adoption.

Read the parent TASK-2622 and the dated inventory before implementation. This task authorizes only its bounded migration slice; task creation did not authorize execution of the wave.

Preserve distinct behavioral guarantees and historical failure modes, not just line totals. Keep task IDs as regression provenance within behavior-owned suites. Inventory file ownership is provisional: review each assertion and route mixed suites to the contract that owns it. Do not make the inventory a second executable selection authority.

Coverage comparison uses exact source/line identities for unchanged source. Intentional production refactors require a reviewed mapping from baseline executable statements to replacement statements, preserving every previously covered path; never manufacture parity by excluding files or executable code. Report the resulting executable denominator and require a nondecreasing comparable line-coverage rate plus coverage of the mapped baseline statements. New executable statements retain the existing new-code quality gate.

Keep unit, integration-ci, integration-local, and agent-e2e obligations and default skip policy intact. Update the existing selection/category/partition authorities when paths change; do not silently omit moved files or expand shared execution based on a text screen alone. New integration tests require classification and local-only dependency reasons. No giant files: production <=500 lines and tests <=1000 except existing explicit debt.

Use focused verification plus ./scripts/verify-local.sh static-analysis for code changes. Check plain unit headroom with npm test -- --unit-test-headroom. Code edits require graphify update .; live documentation edits require docs standards and ./scripts/verify-local.sh docs. Do not run full gates repeatedly in every slice; TASK-2622.20 owns final complete certification.
### Scheduling

Prerequisites: TASK-2622.17, TASK-2622.19. Evaluate reuse only after all migrated inputs and the authoring/discovery policy have settled.

Complete prerequisites through the repository workflow before starting dependent implementation; parallel work requires disjoint file/fixture ownership. Evaluation tasks unlock dependents through an explicit adopt/reject disposition, not through a promised speedup. If architecture change is needed, pause dependent work for the user discussion required by the architecture constraint.


### Architecture constraint

Preserve the existing ports-and-adapters architecture, dependency direction, typed application ports, composition authority, and adapter boundaries. Performance work must fit those boundaries; a speedup does not justify bypassing ports, importing concrete adapters into application/domain code, adding service location, weakening architecture guards, or creating parallel production composition for tests.

Cohesive implementation changes inside existing boundaries are in scope when supported by measured evidence. If investigation shows that the general architecture itself causes a material bottleneck and a solution requires changing its principles or boundaries, stop that dependent implementation and bring the evidence, alternatives, behavioral risks, and proposed architectural decision to the user for a broader discussion. Continue independent work that preserves the architecture. This wave does not authorize an architectural exception or rewrite; any such change needs an explicit subsequent decision before implementation.
