## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Base: TASK-2500. Mission 1 of 6. Introduce an explicit repository-level integration strategy so Parallix no longer implicitly assumes `px integrate` always owns the final merge into the primary branch.

SUPPORTED MODES:
- `local` — GitHub-unaware/local-first. Parallix owns integration into the configured primary branch. Default; preserves current behaviour.
- `github-publish` — fast single-developer. Parallix integrates locally; GitHub independently verifies the exact resulting commit; verified commits publish to protected `origin/main` in order.
- `github-pr` — collaborative. Parallix completes + reviews a mission branch, pushes it, GitHub/PR owns final integration. Parallix must NOT locally merge into remote primary.

CONSTRAINTS (hold across all missions):
- `local` stays first-class: no GitHub config/credentials/network required.
- review approved ≠ integrated into primary. Review authority and merge authority are separate.
- external evidence is OBSERVED from GitHub, not self-asserted via a local boolean.
- exact-SHA differs by mode: `github-publish` pins the same SHA; `github-pr` permits a different GitHub merge/squash/rebase SHA and verifies the resulting relationship/tree.
- GitHub latency must not become agent-development latency (esp. github-publish: verification gates publication, not the next local mission).
- fail closed at authority boundaries.

DEPENDENCY ORDER: base TASK-2500. Mission 1 is the shared foundation — Missions 2 and 3 build on its abstraction. Mission 4 runs in parallel.
<!-- SECTION:DESCRIPTION:END -->

## Mission Requirements

- Add explicit config, e.g. `{ "integration": { "mode": "local" } }`, following existing repo-config conventions (`config/workflow.config.json`, `config/state-map.json`, schema). No explicit mode ⇒ `local`.
- Allowed values: `local`, `github-publish`, `github-pr`. Unknown/invalid ⇒ fail closed with an actionable configuration error.
- Do NOT spread mode conditionals throughout `integrate.ts`.
- Introduce a strategy/capability boundary for: `prepare integration`, `run required local gates`, `produce integration candidate`, `submit for external verification`, `publish`, `observe external integration`, `close mission`. Not every mode implements every operation.
- Domain/application layer expresses integration state and required evidence WITHOUT depending directly on GitHub APIs.
- `local` remains behaviourally identical to current workflow.
- CLI/status surfaces show the active integration mode where relevant.
