## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
When codex's usage quota (weekly window) is spent, Parallix blocks codex for the 1-hour fallback instead of until the real reset, so the pinned review retries and fails every hour.

Evidence (operator workstation, 2026-11-21, review of task-2866.02): log shows `Limit hit detected for codex; reset estimate "2026-11-21 11" (fallback)` while the account was blocked until Nov 22 ~05:58 local. The codex rollout for that launch (rollout under the mission's .workflow/codex-home) ends with `task_complete.error.codex_error_info = "usage_limit_exceeded"`, but its last `token_count` event has `rate_limits: { limit_id: "premium", primary: null, secondary: null }`. When the provider rejects a turn at start, the rollout carries no reset instant, so `rolloutFailureReason` in codex.ts emits `agent-quota` without `resetAt`, and `quotaLimit` in agent-limit.ts falls back to +1h. The only place the reset appears in the rollout is the human message ("try again at Nov 22nd, 2026 5:58 AM"), which must not be parsed.

Structured source verified live: `codex app-server` (stdio JSON-RPC, codex-cli 0.171.0) answers `initialize` then `account/rateLimits/read` with `ordinaryUsageAllowed: false` and `rateLimits.primary = { usedPercent: 100, windowDurationMins: 10080, resetsAt: 1795323483 }` (epoch seconds, matches the message time), plus `secondary` and `rateLimitReachedType`. Schema is generated by `codex app-server generate-json-schema` (GetAccountRateLimitsResponse).

Direction: keep the rollout `rate_limits` as the first source. When the rollout reports `usage_limit_exceeded` but no reset, ask the existing codex adapter to read `account/rateLimits/read` through app-server using the same CODEX_HOME as the failed run (auth is linked into it) and set `resetAt` from the exhausted window(s). When both primary and secondary exist, use the reset of the window(s) that are at or above 100 percent (latest of them), not blindly primary; apply the same selection to the rollout snapshot, which today reads only primary. If the probe fails or reports no exhausted window, keep today's fallback block and fail closed (no string matching of provider messages). Reuse the existing codex adapter, telemetry and failure-reason owners; no parallel limit-detection path. The probe needs a bounded timeout and must not hang or leak the app-server process.

Out of scope: other agents, changing block durations for non-codex agents, parsing message text, gate or CPU budget changes.
