## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`Average PR fix rounds to complete mission` reports `0.00` for every
model-labeled agent because the field it counts is never written.

Observed for 2026-08-02 → 2026-08-08: `claude-opus-5` 4 missions / 0.00,
`gpt-5.6-terra` 5 missions / 0.00, `mixed` 1 / 0.00, `custom` 7 / 0.43. Missions
in that window did receive change requests, so the metric is wrong, not the
workflow.

Chain of causes:

1. `deriveImplementerAndFixRounds` (`src/adapters/cli/commands/stats.ts:1634`)
   treats the `Review` aggregate as the authority and counts
   `rounds.filter((round) => round.decision?.kind === 'changes-requested').length`
   (`:1650`).
2. The only domain function that can write such a decision,
   `applyReviewerCommand` (`src/domain/review.ts:463`), has no caller outside
   the domain module — the only references are the domain definition itself and
   a documentation anchor in
   `src/application/persistence-domain-map.ts:70`.
3. The live loop persists review progress through
   `ReviewState.save` → `applyReviewStateToReview`
   (`src/adapters/review/review-state.ts:573`,
   `src/adapters/review/review-state-mapping.ts:134`). Its
   `decisionFromState` (`review-state-mapping.ts:63`) only produces a decision
   for `phase === 'approved'`; for `phase === 'fixing'` it returns `null` unless
   the round *already* carries a `changes-requested` decision
   (`if (previous?.kind !== 'changes-requested') { return null; }`). Nothing ever
   creates the first one, so the retain-only branch can never fire.
4. Consequently every round has `decision: null` or `approved`, the count is
   always `0`, and because the aggregate branch returns early with
   `source: 'review-aggregate'`, it short-circuits the PR-comment and
   branch-history fallbacks (`stats.ts:1655-1666`) that used to count real
   rounds. `custom` is non-zero only because those missions have no `Review`
   aggregate and therefore reach the fallback.
5. `summarizeAgentWindow` (`stats.ts:943-995`) then averages the stored zeros,
   and the same zeros feed the board's `reviewLoopRate`
   (`src/application/projections/metrics.ts:212`) via `pr_fix_rounds`
   (`src/application/projections/metrics-read-adapter.ts:113`).

Sources that *do* record the rounds and can be counted instead:

- `mission_review_events` (`migrations/0010-review-events-and-implementer-response.sql:25`)
  persists reviewer events with `disposition` and `verdict`, written by
  `persistEventInStore` (`src/adapters/review/review-events.ts:690-736`).
- The round sequence itself: `applyReviewStateToReview` grows `rounds` as the
  loop advances (`review-state-mapping.ts:139-151`), so rounds beyond the first
  are fix rounds.
- `review → active` lane transitions, once task-2347.02 makes them complete.

### Required fix

Make one recorded source authoritative for the fix-round count, count from it,
and stop returning a confident `0` from a path that structurally cannot observe
a change request. Either record reviewer decisions on the aggregate (route the
reviewer outcome through `applyReviewerCommand` with its findings) or count from
`mission_review_events` / the round sequence — but a mission whose count cannot
be determined must report unknown rather than zero. Rename the metric to match
what it counts, and backfill or invalidate the stored zeros already in
`usage_statistics` so historical weeks are not silently wrong.
