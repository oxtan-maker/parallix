## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`medianCycleTimeByStateSeries` (`src/application/projections/metrics.ts:230`)
credits the time between two transitions to the state the mission moved *into*,
not the state it occupied during that interval:

```ts
const minutes = (Date.parse(transition.occurredAt) - Date.parse(previous.occurredAt)) / 60_000;
byLane.set(transition.to, [...(byLane.get(transition.to) ?? []), minutes]);
```

For `08:00 backlog→active` followed by `09:00 active→review`, the 60 minutes
were spent in `active` but are recorded against `review`. Every lane row in the
board's "Median cycle time" column (`src/interfaces/tui/flow-panel.tsx:60`) is
therefore shifted by one transition.

The existing tests encode the inverted semantics rather than catching them:
`test/board-metrics.test.ts:252-281` feeds two missions that spend 60 and 120
minutes in `active` and asserts `medianCycleTimeByState` for `review` equals 90.
Fixing the code requires rewriting those expectations, so this is not an
"add a test" change.

For experiment evaluation this bug can reverse a conclusion outright: a change
that shortens review waiting while lengthening implementation time reads as the
exact opposite on the board.

### Required fix

Introduce an explicit lane-interval derivation — for each (repository, mission)
a list of `{ state, enteredAt, exitedAt | null }` records built by replaying the
ordered transition history — and compute every dwell metric from those intervals
instead of from adjacent-transition arithmetic. Open intervals (the mission's
current lane) must be distinguishable from closed ones so dwell and age remain
separate concepts. Correct the fixture expectations in
`test/board-metrics.test.ts` and `test/board-event-metrics-fixture.test.ts` to
the intended semantics and state the semantics in the metric's doc comment.
