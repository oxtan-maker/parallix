## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Let a precomputed POMDP policy choose the next verification action of a mission inside the review step, instead of the fixed sequence (agent review, human review, integration gates). Then collect enough missions to test whether this reduces verification and repair cost. This parent groups the work. Execute the numbered children rather than activating the umbrella as an implementation mission.

Model and method: *Verification, Rework, and Scheduling in Parallix* v0.11, committed as `../parallix-research/research/verification-pomdp/parallix_stochastic_model_v11.tex` (the "model document"; every § reference in this wave means a section of that file). In short:
- the policy is solved offline with SARSOP and stored as a versioned artifact: vectors tagged with actions, plus the model matrices;
- at runtime Parallix derives each mission's belief from its recorded verdicts and picks the next action;
- no solver runs inside Parallix.

Research simulations predict substantially lower verification and repair cost per change. The estimates have known issues, so this wave tests the hypothesis; it does not assume it. The wave makes **no assumption about which orderings the policy will choose**. It must support every order of agent review, integration tests and human review.

## Operator decisions recorded for this wave (2026-11-17)

These change architectural behavior and are decided by the operator; children implement them and do not reopen them.
1. **The review step is generalized** into "next policy action". Agent review, integration tests and human review are all actions inside the review step, chosen by the policy, in any order, until all three have passed on the current change. Human review stays in the review step.
2. **Integration (landing) starts only when all three have passed.** Exception that removes double work: when agent review and integration tests have passed, the human may push integrate directly. That counts as the human approval and moves the mission to integration in one step.
3. **The human is told explicitly when it's their turn.** When the policy chooses human review, the mission shows clearly that human review is due. When the human finishes (approve or request changes), the review step continues with the next policy action.
4. **No human-eligibility restriction.** Human review may be chosen at any point of the review step.
5. **The PX-lead early integration test and the opportunistic integration dry-run (prevalidation) are removed.** The policy becomes the single owner of when verification actions run.
6. **The review-window budget is replaced by an action limit:** after X = 40 actions in the review step, the mission stops and is handed to the human for manual intervention. This covers the long tail.
7. **The fixed sequence stays available** as the fallback and as the sentinel arm, expressed as a fixed policy inside the same generalized review step, not as a second implementation.

### Stage A: policy artifact (research tooling under `../parallix-research/research/verification-pomdp/`, nothing under `src/`, `web/`, `tools/verification/` or `test/lib/`)

**Slice 1: Emit the artifact.** Extend the existing research pipeline (parameters, solver model, alpha-policy parsing, solve command, report) to write the contract-v1 artifact for each objective from a solve: states, named actions, observations, matrices, costs, prior, vectors with action **names**, bounds, parameter hash, solver version, canonical SHA-256. The solver's zero-based action codes are converted in exactly one place. Reuse what exists; add at most 2 new files. No SARSOP code or binary is committed; the pinned build (`https://github.com/AdaCompNUS/sarsop`, `-fcommon` in `CFLAGS` of `src/Makefile`) is documented. The artifact is plain JSON; unknown or missing parameters fail the command and are never defaulted. Cases: row sums, absorbing state 27, numbering against v0.11 Table 3, policy parsing on a small fixture policy file. The README states the v0.11 rules and drops any remaining human-eligibility wording; a `human_eligibility` field in a parameter file is rejected.

**Slice 2: Validate the artifact numerically.** One command produces both artifacts and fails loudly on any numerical validation failure: every row of every matrix sums to 1 within 1e-9; the solver's bound gap is at most 0.1% of the value; an independent Monte Carlo of at least 20,000 missions (undiscounted, every mission to merge) of the artifact's own model has the policy value inside its 95% interval; and the current sequence's value computed by one linear solve `(I − ρP_μ)⁻¹c_μ` agrees with an independent simulation of that sequence on the same model. These checks prove that the solver, the artifact writer and the evaluation code agree with each other on the supplied model. They say nothing about whether the model matches Parallix, and no expected value of the real model is asserted anywhere: the numbers of v0.11 §7.5 only demonstrated the method and are not targets. The pipeline is exercised in tests on small synthetic models with closed-form answers (for example a single check with a known pass probability, repair cost and check cost, whose expected cost is derived by hand in the test). No test invokes SARSOP, the network or the operator database; the solver run is a documented manual step with its output captured in the checkpoint. How well the model fits real mission data is measured and reported in slice 23, not assumed here.

### Stage B: pure policy module (`src/application/`, no IO)

All three slices: no filesystem, clock, process or randomness; no imports from adapters, interfaces or composition; no dependency on Mission, Review, RunRecord or store types (the caller maps those, slices 7–8); no new dependency; matrix work is plain loops over 27 states; no edits to existing production files except one export line if module conventions require it. The module does not decide Parallix rules: `permitted` is an input and it never infers approval or gate success. At most 3 new production files across slices 3–5 together.

**Slice 3: Parse and validate.** `parsePolicyArtifact(json)` returns a typed artifact or a typed rejection (wrong schema version, numbering, dimensions, non-finite numbers, rows not summing to 1 within 1e-9, missing fields) and never throws on bad input. Tested on a hand-written fixture that follows the artifact contract exactly; one case per rejection class.

**Slice 4: Derive the belief.** `deriveBelief(artifact, history)` replays an ordered history and returns `{ belief, record }` or a typed failure (`contradiction`, `unmodelled-history`, `invalid`). History entries, all typed: `verdict` (check, passed or not); `repair` (check); `retained-pass` (check); `unmodelled-change`; and the state "repair pending" (a failed verdict without its completed repair). Replay: start at the prior; a pass applies the filter with observation `passed`; a failure followed by its completed repair applies the filter with `not-passed`, whose transition already contains the repair; a failure whose repair is pending leaves the belief as it was and produces a pending-repair marker, never a recommendation; `unmodelled-change` resets to the prior; `retained-pass(check)` keeps the mass on states where that check would pass, relabels it `passed` and renormalizes (zero mass is a `contradiction`); a verdict with predicted probability 0 returns `contradiction`, never divides by zero. Deterministic for identical inputs. Cases: hand-computed belief for agent pass then tests failure with repair; reset; retained pass; contradiction without NaN or infinity; pending repair; belief finite and summing to 1 within 1e-9 after 200 random fixture steps; identical histories give identical beliefs; belief update equals the research module's filter on random sequences (the test may import the research code, production code may not).

**Slice 5: Recommend.** `recommend(artifact, belief, permitted)` returns the action of the highest vector among those whose action is in `permitted`, with the predicted pass probability of every check (belief mass on states where the check would pass or has passed); no permitted vector returns `no-recommendation`. Cases: empty `permitted`; restricting `permitted` changes the recommendation when the unrestricted best is excluded; on the slice 1 artifact, agreement with the solver's own best vector on at least 1,000 beliefs reached by simulating missions from the artifact's model.

## Pre-registered evaluation (do not change after the pilot starts)

- Design:
  - the next 15 completed policy-arm missions run the policy;
  - the control is recent history: completed missions from the 2–3 weeks before activation, with the same agent and model versions and the same Parallix fixes;
  - 3–5 interleaved fixed-policy sentinel missions run inside the same generalized review step and detect drift and effects of the new mechanics themselves.
- Primary outcome: verification and repair cost per mission in money (assumed cost units, the same formula and prices for both groups). Secondary outcomes: wall time per mission; actions and repairs per mission; missions reaching the action limit.
- Hypothesis (the only one this pilot tests): the POMDP policy selects verification actions better than the fixed sequence, meaning lower verification and repair cost per mission. Test: one-sided, 90% significance, Welch test on log cost, with a rank test as a robustness check. The hypothesis is supported if the policy arm's cost is significantly lower; not supported if it is not; inconclusive only when the data cannot answer (fewer than 15 completed policy-arm missions, or no usable control window). No minimum effect size is pre-set; the effect size and its confidence interval are reported.
- Model fit (reported, not a gate): the report of slice 23 states, with intervals, how far the model's predicted pass probabilities (shadow-mode calibration) and its fixed-sequence actions, repairs and cost per mission are from the observed values. The operator decides in writing whether to start the pilot after reading it; no tolerance is pre-set.
- History stability (reported, not a gate): the two halves of the control window are compared on the same outcomes and the difference is reported with the verdict, so a drifting baseline is visible.
- Known confounders:
  - history used the review-window budget, the pilot uses the action limit. Missions reaching either limit are reported separately; sentinels show the effect of the new mechanics without the policy;
  - history ran integration gates once at landing; a policy-arm mission may run the integration tests as an action and again at landing when no gate evidence covers the landing candidate (corner case 16). Both runs are priced by the same formula and the number of landing re-runs is reported per arm.
- Abort: the operator stops the policy arm if merge rate, manual interventions or human review load are clearly worse than in the control window. "Clearly worse" is made numeric by the operator in slice 24 **before activation**, never afterwards.

## Artifact contract (single definition for slices 1–6)

Children implement against this contract; none of them redefines it. Version 1, plain JSON, one file per objective (`money`, `time`):
- `schemaVersion` (number, 1), `objective`, `parameterHash`, `solverVersion`, `discount` (ρ);
- `states`: 27 entries in the order of v0.11 Table 3, each spelled out as `{ tests, agent, human }` with status `would-fail` | `would-pass` | `passed`. Array position k holds state i = k + 1. State 27 (all `passed`) is absorbing;
- `actions`: exactly `tests`, `agent`, `human`, named, never numbered. Vectors and recommendations carry action **names**, so the solver's zero-based action codes are converted in exactly one place (the parser in slice 1) and an off-by-one cannot reach runtime;
- `observations`: `not-passed`, `passed`;
- `transition` and `observation` matrices per action, `cost` per action and state, `prior` over the 27 states;
- `vectors`: list of `{ action, values[27] }`;
- `bounds` `{ lower, upper }` and `predicted` `{ policyValue, currentSequenceValue }`.

The artifact preserves the model produced by the existing solver from the supplied parameter file. Its 27-state matrices, combined check-and-repair costs and embedded prior are derived outputs, not literal copies of the eight-state input arrays. Do not alter, round, renormalize, smooth or fill in the supplied estimates. The parameter schema has no `discount` field: preserve the solver's default `(1.08)^(-(18.9/22)/8760)` and its explicit `--discount` override, recording the value actually used. Missing required parameter fields still fail; neither a new discount field nor a change to the parameter file is required. The existing `horizon_N` and `terminal_penalty` fields do not enter the infinite-horizon solver. `parameterHash` identifies the exact input file bytes read and validated, rather than reconstructed JSON.

The artifact is identified by the SHA-256 of its canonical bytes; that hash is the "pinned artifact hash" used everywhere in this wave. A hand-written fixture artifact for unit tests lives next to the owning suite of slice 3 and follows this contract exactly.

## Shared hard rules (copied into every child's scope and out-of-scope)

- **Rules that stay authoritative:**
  - merge only when agent, human and integration tests have passed on the current change identity (or via decision 2);
  - repair immediately after a failed check;
  - rebase before every gate run;
  - declared gates remain the preparation of every new revision, outside the model.
- **Safe fallback everywhere.** With the switch off, no artifact, an invalid or mismatched artifact, a history the policy cannot interpret, or any policy error, the mission continues with the fixed policy and the reason is recorded. Policy failures never block, fail or stall a mission.
- **Single owners:** one owner decides the next verification action. Superseded owners (PX-lead early integration, integration dry-run, review-window budget) are removed with their tests in the same mission that supersedes them, after the replacement is wired into every production caller (AGENTS.md "Implementation").
- **No edits outside the wave's decisions to:**
  - verification gates and `tools/verification/**`, CPU budgets, retry budgets;
  - reviewer selection or policy, approval-coverage rules, rebase policy;
  - integration-gate disposition or repair routing for landing;
  - ADRs other than the one recording these decisions, domain-guard rules, consumer-domain requirements' meaning, migration checksums. A guard that names a symbol, file or anchor this wave renames or removes gets a mechanical anchor update in the same mission, reported in the checkpoint. A guard whose *rule* blocks the design means stop and ask the operator (never weaken it, never add a parallel guard).
- **No new database columns or migrations** unless a child's checkpoint shows that no existing owner can hold the data and the operator approves. Any new status, phase or transition beyond the operator decisions above needs the same approval.
- **No fabricated statistics.** Unknown values stay unknown, never 0 (cf. PX-0056). Existing metrics keep their meaning; new action types are recorded explicitly.
- **Model parameters are operator data, never agent output.** Probabilities (prior and repair rows), costs, the discount and the current-sequence policy come only from the operator-supplied parameter file of the estimation mission (px-0060 and its successors). No slice estimates, tunes, rounds, completes, defaults or "fills in" a parameter, and none reconstructs one from the model document's prose. **Numbers pass through unchanged:** every probability, cost, prior and discount in an artifact is exactly the value in the operator's parameter file (no rounding, renormalizing, smoothing or defaulting; a file that fails validation is rejected, not repaired), and the artifact records the SHA-256 of that input file. The wave moves the numbers into the runtime's data format and nothing else. **Runtime never depends on `research/`:** `src/` and `web/` import, read and name nothing under `research/`; the runtime reads one artifact from the operator-configured path (`verificationPolicy.artifact`) and contains no parameter values at all. Only tests may import research code, to cross-check. The wave commits no copy of the operator's real parameters. Test fixtures are small synthetic inputs, labelled synthetic in the file and the case name, never reused as parameters outside tests, and never described as estimates. Anything that needs a real parameter and does not have the operator's file is reported as not exercised and the mission stops for the operator.
- **SARSOP (GPL-2) is offline research tooling only.** It is never imported, bundled or invoked by the Parallix runtime.
- **Per-child size:** every slice is Small or Medium (at most 235 NEL, ADR 0047). If the honest estimate is larger, stop and split the slice at a boundary named in its description; never pack files to fit, never raise the bucket, never record Large on a child.
- The research pipeline is in the private workspace under `../parallix-research/research/verification-pomdp/` (model, solver model, alpha-policy parsing, current-policy evaluation, report). Reuse and extend it; do not write a second one. Revalidate every other referenced owner against the active tree.
- Read ADR 0057 before choosing tests and extend owning suites. Unit cases meet the 500 ms headroom requirement; new or changed integration tests stay within 3.5 s. Manually exercise behavior with a disposable `PARALLIX_HOME`; never touch the operator database outside the switched-on pilot.

## Wave integrity and agent-slop guardrails

Source: the repository's bug history. Each rule names the failure class it prevents. Every child applies the rules marked for it; the checkpoint of each child states, per applicable rule, how the change satisfies it or why it does not apply.

**Integrity of the wave (Parallix must work after every child, never only after a later one)**

- **W1. Every child lands on its own.** After any child is integrated, `main` must run every mission exactly as before it, with the switch off or absent. The only behavior changes in the wave are the ones assigned by decisions 1–7, and only slices 17, 19, 20 and 21 make them (slice 17 for every mission; slices 19–21 behind the pilot switch or the limit as stated). A slice that cannot keep Parallix working without a later slice stops and reports; it never lands "temporarily broken", never adds a compatibility shim to bridge the gap, and never leaves a TODO for the next slice (prior waves needed repair missions TASK-2766, TASK-2769, TASK-2770 and TASK-2817 after exactly this pattern).
- **W2. Parity traces first.** Before the first behavior-affecting edit, slice 11 captures from the parent commit golden traces of today's fixed sequence: all pass; agent failure and repair; human send-back; integration gate failure and repair; retained approval; restart mid-action. Parity tests compare the sequence of actions, lifecycle events and existing statistics against these traces. Traces are recorded from the real owners, not hand-written from expectations. Parity assertions are never edited to match new behavior; a difference is either an operator decision from this wave (listed) or a defect.
- **W3. Only pure additive code may be unwired.** The policy module (slices 3–5) and the domain rules of slice 13 may land without a production caller because they are pure, additive and exercised by their unit suites; the first slice that needs them wires them (slices 6–9 and 15–19). Slice 14's executor is reachable through the next-action owner but chosen by no policy until slices 17 and 19. Nothing else in the wave ships exported-but-unused production code. The domain-architecture, single-path, rebound-kernel and consumer-domain guards must be green at each landing.
- **W4. Activation order.** `pilot` has no behavioral effect before slice 19 is integrated. Between slices 19 and 21 every mode, including pilot with non-fixed orders, has a finite termination bound (the existing review-window allowance counts every policy action; slice 19 proves termination with a test where every check fails forever). Slice 24 may not activate the pilot before slice 21 is integrated and slice 23's report ran on shadow records.
- **W5. Switch off means off.** With mode `off` or no `verificationPolicy` block: no artifact read, no history read, no record written, no extra query, and the fixed policy runs. Invalid configuration for this block disables the block and is reported once; it must not prevent `px` from starting.

**One owner, no parallel paths** (TASK-2817, TASK-2832, TASK-2818, TASK-2842)

- **W6.** Before editing, list every production entry that can start, resume, or finish a verification action: `px review` and its recovery, board commands, the automatic review loop, the recovery supervisor and lead, `px integrate`, rebase and rebound workflows. Migrate all of them to the one next-action owner. No second resume handler, wrapper over old and new, interface-specific state machine, feature-flagged fallback to the old code, or catch-and-retry workaround survives.
- **W7. Repairs stay in the kernel.** Policy-chosen repairs launch the implementer only through the existing rebound kernel (`test/unit/application/rebound-kernel-only-guard.test.ts` fails on any new agent launch outside it). Gate runs reuse the existing gate and rebase owners; a policy action never calls them through a new path.
- **W8. One writer per event.** Lifecycle and board lane transitions keep their existing writer and idempotency keys. A new record or event has exactly one writer and an idempotency key derived from mission, change identity and action sequence, so a restart or a concurrent entry cannot write it twice (the double-collected lane transitions of TASK-2842).
- **W9. Concurrent entries.** Two actors (operator command, recovery supervisor, lead, second terminal) cannot start two actions for one mission. Use the existing recovery claim and operation ownership; the second actor gets a refusal that names the owner, never a duplicate run.

**Control flow completes** (TASK-2766, TASK-2757, TASK-2806, TASK-2582, TASK-2833, TASK-2824)

- **W10. Every action has a completion edge.** For each action and each verdict (pass, fail, agent exit without verdict, timeout, interruption), a test proves control returns to the next-action owner or to an explicit human hand-off with a typed reason. An early `return`, an exit-0 that is treated as success, or a coordinator left alive and idle is a defect. Agent exit code 0 never completes a check or repair; only the check's own verdict does.
- **W11. No stranded state.** Slice 11 includes a table-driven test over (mission status × review phase × pending repair × check validity × approval coverage) proving the next-action owner always returns a defined action, a wait, or a typed hand-off. "Approved but repair pending" and "active with undecided round" are rows, not afterthoughts.
- **W12. Domain owns legality** (TASK-2679, TASK-2582, TASK-2673, TASK-2641). Legal lifecycle and review-phase transitions stay pure domain rules; human-first, tests-first and any other order are checked against them exhaustively. A transition failure is never swallowed or reported as success. Integration tests run as an action never require landing eligibility (an approved review, lane `integration`) and never fabricate an approval to pass a preflight. Human approval before agent review, and an agent request-changes after human approval, are explicit cases.

**Preserve what exists** (TASK-2709, TASK-2744, TASK-2793, TASK-2804, TASK-2818, TASK-2832, TASK-2685)

- **W13. Existing statistics keep their meaning.** A golden statistics fixture (review rounds, human send-backs, stage statistics, flow projections) is computed before and after each child that touches records, and is identical for existing metrics. New action types appear as new, separately labelled entries. Integrate-as-human-approval counts once, not as both an approval and a handoff.
- **W14. Identity and configuration flow through every action:** implementer assignment and launcher configuration, composed environment, reviewer configuration, repository, MissionId. Each action's test asserts the values it received, not only that it ran.
- **W15. Human-visible turns are attention items.** "Human review due" and "action limit reached" appear wherever human-only blockers already appear (attention, lead view, CLI status, board), derived from authoritative mission state (TASK-2799, TASK-2814). Hand-off reasons are typed failure reasons that survive recovery (TASK-2829), not free text.

**Cost, speed, evidence** (TASK-2770, TASK-2854, TASK-2646, TASK-2769)

- **W16. No cost on the read path.** Board, flow and status additions read stored decision records; they never replay mission history or evaluate the policy per card per refresh, never add per-card subprocesses, and are exercised on a production-shaped populated fixture, not an empty one (the cold-observer timeout loop of TASK-2770 passed an empty-directory smoke).
- **W17. Reuse claims are measured.** Reusing a passing test action at landing depends on gate evidence that today is keyed to the exact head; bookkeeping commits and rebases move it (TASK-2646). Before relying on reuse, the child measures on a real rebound flow whether the evidence can ever cover the landing candidate and states the result. No new validation-marker mechanism is added; if reuse never applies, landing re-runs the gates and the cost is counted.
- **W18. Evidence is real.** Checkpoints separate source inspection, automated checks and manual observations. A scenario that was not exercised is reported as not exercised. No invented latency or counts, no red-on-parent claim without running it, no unit-test-only delivery of a behavior that needs an end-to-end exercise.
- **W19. Tests tell the truth.** No weakened assertions, no changed expectation that blesses a bug, no mocking of the boundary a case claims to prove, no new skips, no raised CPU or retry budgets, no new verification gates. A removed owner's tests are deleted only after the checkpoint lists each distinct behavioral assertion and where it now lives.
- **W20. Guard and test hygiene** (repository memory and AGENTS.md). Edit existing guards in place; never add a parallel one. Cite file and symbol, never a line number, from one file into another's guard. Do not run full test gates or whole-project type checks as a batch; run focused suites and scratch reproductions, CI owns the rest. Evidence is recorded through `px checkpoint record` only; no mission files, no direct database access, nothing in `backlog/archive`.

## Corner cases the wave must handle (owner slices in brackets)

1. Restart or recovery supervisor mid-mission: the belief and the next action are rederived from recorded history; nothing depends on in-memory state [slices 4, 7, 9, 12, 19].
2. Artifact republished while missions are in flight: each mission keeps the artifact hash pinned at entry; if unavailable it continues with the fixed policy [slices 6, 18].
3. Clean rebase with an unchanged change identity: verdicts remain valid, and the belief is unchanged [slices 4, 8].
4. Change identity changed by a conflict-resolving rebase, re-scope or any code change outside a modelled repair: recorded as an unmodelled code change; the belief resets to the prior and all three checks are owed again [slices 4, 8, 19].
5. Declared gates failing on a new revision: outside the model; recorded as an unmodelled code change [slices 8, 10, 19].
6. Several agent reviewers in one round: only the authoritative round outcome is a verdict [slices 7, 9].
7. Approvals retained across a repair by approval coverage: that check stays passed in the solver state [slices 4, 8, 13].
8. A verdict the belief gives probability 0: cannot arise from the policy itself (it never re-runs a passed check on the same change). It can only come from a manual re-run or a history-mapping bug, so it is treated as a bug detector: the mission falls back to the fixed policy and it is flagged; never divide by zero [slices 4, 19].
9. Human review chosen before agent review or tests: allowed; the human sees whatever evidence exists so far [slices 13, 15].
10. Human pushes integrate while agent and tests have passed but human review has not been recorded: counts as human approval and moves to integration (decision 2). In any other state, integrate is refused with a clear message [slices 16].
11. Human requests changes: routed to a human repair; the next policy action follows [slices 13, 15].
12. Operator manual commands overriding the policy (review, integrate, cancel, drag and drop): recorded as overrides; the verdicts still update the belief [slices 9, 19].
13. Action limit reached: the mission stops and is handed to the human with a clear reason; counted separately [slices 20].
14. Escalations, PX-lead recoveries and rebase conflicts: outside the model; no policy decision during them [slices 9, 12, 19].
15. Switch changed mid-mission: the mission finishes on the policy it started with, or on the fixed policy if the switch is turned off; recorded [slices 6, 9, 18].
16. A passing integration-test action reused at landing: only when existing gate-evidence coverage proves it covers the landing candidate after the final rebase; otherwise the gates run again and the cost is counted [slices 14, 17].
17. Board, cards, commands and flow projections: show truthfully whose turn it is and which action is next; no projection assumes the fixed order [slices 15].
18. Cancelled or abandoned missions: excluded from the primary outcome but counted and reported [slices 23].
19. Belief numerics: rows sum to 1, no underflow to all zeros, deterministic results for identical histories [slices 4, 5].
20. A failed check whose repair has not completed yet (including a repair interrupted by a restart): the history is "repair pending", the repair is not a policy decision, and the belief is only updated when the repair completes [slices 4, 7, 12].
21. A repair that addresses the findings of more than one check, or a check run on a revision other than the current one: outside the model; recorded as an unmodelled code change, never mapped to the nearest modelled repair [slices 8].
22. Integration gate failure at landing after all three passed (existing rebound and repair routing, unchanged): recorded as a failed tests verdict plus its repair; which approvals survive is decided by existing approval coverage; the review step then continues [slices 8, 17].
23. Two actors start an action for one mission at the same time (operator command, recovery supervisor, second terminal): exactly one runs, the other is refused naming the owner [slices 12, 19].
24. Arm assignment at entry (policy or sentinel) is persisted once, derived from recorded entries rather than an in-memory counter, and is safe when two missions enter at once [slices 18].
