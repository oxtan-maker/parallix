## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Prove that the checked domain can express each behavior the migration and UI require before adding tables or adapter records. Map requirements to the current names Mission, CheckpointData, Review, MissionOutcome, AgentRunMeasurement, KnownRepository, SessionMarker, LaneTransitionEvent, and AgentBlock. Add a domain concept only when a current consumer needs identity, lifecycle, or invariants that these concepts cannot represent. In particular, do not infer an Attempt entity from legacy files or a convenient schema shape.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Every database-owned concern in the executable inventory maps to a checked domain type and invariant, or is documented and tested as technical persistence metadata rather than a domain entity.
- [ ] #2 Current launch, retry, failover, usage, review, and UI consumers are traced to the domain information they require, using the names and boundaries present in checked source code.
- [ ] #3 If per-launch identity or lifecycle is required, an Attempt domain model is introduced with stable identity, invariants, relationships to Mission, SessionMarker, and AgentRunMeasurement, domain tests, and an ADR 0053 update before any Attempt table or adapter is permitted.
- [ ] #4 If an Attempt is not required, the evidence and architecture tests state which existing concepts satisfy every current consumer and prevent persistence code from introducing an Attempt record implicitly.
- [ ] #5 Any other required domain extension follows the same sequence: consumer need, checked type and invariants, domain tests, ADR 0053 decision, then later persistence work.
- [ ] #6 This task adds no SQLite schema, migration, legacy import, command cutover, or file-format compatibility logic.
<!-- AC:END -->
