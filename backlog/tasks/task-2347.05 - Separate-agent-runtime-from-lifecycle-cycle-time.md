## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The board reports agent execution minutes under the name "cycle time".

`ConcreteMetricsReadAdapter.usageRecordsToOutcomes`
(`src/application/projections/metrics-read-adapter.ts:112`) builds
`cycleTimeMinutes` by summing `record.duration_minutes` across a mission's usage
rows, and sets `runs: []` (`:126`), discarding the per-run measurement detail
entirely. `medianStateTimes` then presents that sum as the mission's cycle time.

These are different quantities. A mission that activates Monday 10:00, runs an
agent for 22 minutes, waits overnight, takes 15 minutes of review and closes
Tuesday 12:00 has ~37 minutes of agent runtime and ~26 hours of lifecycle cycle
time. The domain already distinguishes them: `AgentRunMeasurement` carries
execution duration, tokens, tool calls and provider/model, while
`MissionOutcome.cycleTimeMinutes` and `CompletedMissionStatistics`
(`src/domain/usage.ts:114`) model the lifecycle outcome separately.

Consequence: the board cannot answer either question. Agent efficiency is
polluted by queueing, and delivery-system efficiency is invisible — which is
precisely the comparison the statistics exist to support.

### Required fix

Compute lifecycle cycle time from the lifecycle event history (`closedAt`
minus backlog entry, with waiting time visible per lane via the intervals from
task-2347.03) and keep agent runtime, tokens, cost and tool calls as separate
run-level measurements carried on the outcome. Surface both on the board under
names that cannot be confused, and stop emitting `runs: []`.
