## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Introduce the single rebound kernel — the one path every failure-mode improvement reuses — and land it on the incident path (pre-review gate and hook bounces, replacing the current auto-bounce in the review-loop gate handling).

**Contract** (application layer):

- `rebound(reason, context) -> outcome`
- `reason` is a structured value: gate failure (area, command, exit code, stdout, stderr — from TASK-2377.02's typed evidence), hook failure (hook identity from git state, output), artifact-incomplete (role, diagnostic), agent-timeout (role), handoff-verification (error, gate output). Never a regex match on combined text.
- `context` carries slug, worktree, implementer, and a `verify` callback that re-runs the failing check and returns pass/fail with a fresh diagnostic.
- `outcome` is `fixed` (verify passed), `exhausted` (budget spent, mission stranded with the last diagnostic), or `human-only` (classification says no agent can fix it).

**The kernel owns, once:**

1. **Classification** — the single ADR-0048 table. The ad-hoc human-only override regex is folded in as a rule inside the classifier; the remap that relabels every non-hook gate failure as a Git blocker is deleted and the `GateFailure` dispatch is restored. No per-site override logic survives.
2. **Fix prompt** — one builder with slots (kind, mission, area, diagnostic, attempt, "the check re-runs automatically after your fix" — true because of the verify loop). The context-compaction boilerplate lives in exactly one place.
3. **Launch** — `startAgent`, with an ambiguous null exit status reclassified as launch failure (a null-exit "fix" is no evidence of a fix).
4. **The verify loop** — launch agent → run `verify()` → pass: `fixed`; fail with budget left: relaunch with the fresh diagnostic; budget spent: `exhausted`. A bounce is reported as fixed **only when the failing check re-runs and passes**.

**Budget — per local failure (deliberate policy, replaces cumulative persisted counters):** each `rebound()` invocation is one failing occurrence with a fresh in-memory budget (default 2 attempts). Nothing is persisted across occurrences; an occurrence that exhausts its budget strands, and the *next* occurrence of the same failure class starts fresh. No counters in review-state metadata, no SQLite retry columns, no cross-process shared budget. (Removal of the existing persisted state is TASK-2377.04.)

**First consumer:** the pre-review gate and hook bounces. The gate path's existing behavior (bounce, then re-run rebase+gate) becomes the kernel's verify loop. The hook path's missing re-run is closed: its `verify` re-runs the in-process pre-review rebase plus the verification gate, so "implementer relaunched" is no longer an unverified claim.

Out of scope: other bounce paths (TASK-2377.04 / .05), deleting the persisted counters (TASK-2377.04).

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 The kernel exposes the contract above and is the only code path that launches an agent for a pre-review gate or hook failure.
- [ ] #2 A bounce outcome is `fixed` only when the verify callback passes; a failing verify consumes the per-occurrence budget and relaunches with the fresh diagnostic; exhaustion returns `exhausted` with the last diagnostic and strands the mission.
- [ ] #3 Budget is per local failure: in-memory per invocation, default 2 attempts; a second occurrence of the same failure class after an exhausted one gets a fresh budget; no state is written to review-state metadata or SQLite by the kernel.
- [ ] #4 An ambiguous null agent exit status is treated as launch failure, not success.
- [ ] #5 Classification is the single ADR-0048 table: the human-only override is a rule inside the classifier, the Git-blocker remap is deleted, and a declared gate that ran and exited non-zero dispatches as a gate failure.
- [ ] #6 One fix-prompt builder serves all kinds; the pre-review gate and hook prompts no longer duplicate boilerplate.
- [ ] #7 The rebounce reproduction suite (task-2353) and pre-review gate suites (per-round gate, gate-failure prompt) stay green, with any expectation changes documented in the checkpoint.
