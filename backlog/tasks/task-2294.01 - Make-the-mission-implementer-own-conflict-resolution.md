## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Conflict handling currently launches the `conflict-resolution` step without pinning the mission's recorded implementer. A separate eligibility list in `config/agents.json` can therefore assign conflict work to an unrelated family, and launcher fallback can silently change the actor again after a block, capacity failure, missing launcher, or usage limit. This contradicts the target domain model: conflict resolution is implementation work owned by the mission implementer, while `conflict-resolution` is the reason tokens were consumed, not a separately assignable role.

Align both conflict entry points (`px rebase` and `px resolve-conflict`) with that ownership rule. Resolve the implementer from the current mission driver through the existing adapter boundary, pass the mission/role identity needed for session and usage attribution, and fail with explicit recoverable guidance when the recorded implementer cannot run. Parallix must not select a substitute conflict resolver from a separate pool. Keep the solution open to configured future agent families and local-first operation; do not introduce Forgejo as a requirement.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria

- [ ] #1 Both `px rebase` and `px resolve-conflict` launch agent-assisted conflict work as the mission's recorded implementer, with the mission slug and `implementer` role carried into the launch.
- [ ] #2 No `conflict-resolution` eligibility pool, weight, default family list, or family-specific resolver hardcoding remains in executable configuration, runtime selection, examples, or operator documentation.
- [ ] #3 A blocked, capacity-constrained, unavailable, or usage-limited mission implementer is not silently replaced by another family; the command fails clearly and leaves or reports a recoverable Git state and next action.
- [ ] #4 Conflict resolution accepts any agent family that is valid for the recorded mission implementer, including configured future families, without adding built-in family names to the conflict path.
- [ ] #5 The ownership rule works without Forgejo and resolves mission identity through the active mission-driver adapter rather than treating PR-provider data as authoritative.
- [ ] #6 Fast hermetic tests cover both conflict entry points, implementer pinning, missing implementer, and unavailable/limited implementer behavior without launching a real agent or accessing Forgejo.
- [ ] #7 Conflict-resolution usage remains attributable to the `conflict-resolution` work stage and the `implementer` role; any runtime telemetry changes required for that attribution are covered by focused tests.
- [ ] #8 Operator documentation describes conflict resolution as implementer-owned work and no longer presents it as a separately configurable workflow step.
- [ ] #9 `./scripts/verify-local.sh all` and the applicable static-analysis gate pass.
