## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Part of wave TASK-2521 (read its architectural constraints and mandatory agent-slop checks; they apply here).

Depends on: Mission 1 (TASK-2521.01). Can proceed in parallel with Mission 3 (TASK-2521.03) after shared Mission boundaries are stable.

Purpose: allow Parallix to self-host without keeping `backlog/tasks`, `backlog/completed`, `backlog/archive`, or `backlog.md` as its own planning database.

### Architectural boundary

The local task catalog is a task-source concern, not part of the Mission aggregate.

It may use the same physical `<PARALLIX_HOME>/parallix.db` but must remain behind the existing task-source/application boundary.

Do not add task lifecycle fields to Mission merely because the old files contain them.

### Work

* Implement a local SQLite-backed task provider using the current task-source port/contracts.
* Persist only fields justified by the task-source semantics that Parallix itself uses.
* Support current Parallix planning operations needed by CLI/board/mission intake.
* Preserve ability to use external task providers where that is already part of product behavior.
* Build an explicit one-way importer for legacy Parallix task files:
  * `backlog/tasks/**`;
  * `backlog/completed/**`;
  * `backlog/archive/**`;
  * relevant `backlog.md` material if it still contains unique information.
* Importer must:
  * support dry-run;
  * be idempotent;
  * identify source task ID;
  * detect duplicate disagreement rather than choose a winner silently;
  * report malformed/unrepresented fields;
  * not overwrite newer canonical data silently;
  * provide counts for discovered/importable/already-imported/conflicting/unrepresented records.
* Normal runtime must not use this importer as a fallback task reader.
<!-- SECTION:DESCRIPTION:END -->
