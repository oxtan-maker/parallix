## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-2332.08 added an `adapter-owned-workflow-sequencing` rule to the architecture guard that flags any module under `src/adapters/` importing three or more distinct sibling adapter packages. The threshold is arbitrary: it cannot distinguish an adapter that legitimately uses three mechanisms from one that sequences a multi-integration workflow.

The consequence is a guard that can never be turned on. With TASK-2332.15 merged, the rule reports 23 production modules — not only `src/adapters/cli/commands/`, but mechanism adapters such as `git`, `forgejo`, `verification` and `agents`. Its tree-wide zero-violation assertion in `test/dependency-graph.test.ts` is therefore `test.skip`, so the rule proves nothing about the real tree; only its fixtures and its diagnostics are exercised.

A rule that is permanently skipped is not a guard. Either state the ownership invariant in a form the canonical tree can satisfy, or remove the rule and stop implying the tree is protected. Adding an allowlist, grandfather list or path exemption is not an acceptable resolution — the parent mission's restricted areas forbid it, and it would recreate the directory-placement bypass the rule was meant to close.

Whoever picks this up should first decide what "workflow sequencing" actually means structurally (candidates: depending on the `cli` adapter package, depending on more than one *integration* package as opposed to a host mechanism, or constructing multiple collaborators rather than receiving them), then either enforce that tree-wide or retire the rule with the reasoning recorded.
<!-- SECTION:DESCRIPTION:END -->
