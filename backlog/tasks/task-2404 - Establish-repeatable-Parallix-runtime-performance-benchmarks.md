## Description

<!-- SECTION:DESCRIPTION:BEGIN -->

Create a small, repeatable performance measurement harness for Parallix so future optimization decisions are based on evidence rather than intuition.

This is a MEASUREMENT mission, not an optimization mission. Do not lazy-load CLI commands, rewrite production algorithms, add caches, change board behavior or otherwise "fix" measured bottlenecks here.

Establish reproducible measurements for at least:

- CLI cold start / `px --version`
- `px status <slug>` against a controlled representative repository/fixture
- `px stats` against a controlled representative repository/fixture
- one complete BoardProjection build for representative mission counts
- scaling of BoardProjection build across at least a small and materially larger mission set

Where useful, report more than wall-clock time. For board/status measurements capture deterministic work counters through existing seams or benchmark-only instrumentation, including at least:

- Git subprocess count
- `git worktree list` invocation count
- SQLite query count
- task-document filesystem read count

The benchmark should make structural regressions visible. A 10 ms timing difference on one machine is weak evidence; changing from 2 Git subprocesses to 200 when mission count grows is strong evidence.

Use warmups and multiple samples for elapsed-time benchmarks and report robust summary values such as median and a tail value rather than one invocation. Keep machine/environment information sufficient to interpret results.

Do not add a large benchmark dependency unless it materially improves the implementation. A small Node-based harness using `process.hrtime.bigint()` and controlled child-process runs is acceptable.

Do not commit a permanently authoritative Markdown document full of benchmark numbers that immediately becomes stale. Benchmark results belong in mission/checkpoint evidence or optionally machine-readable output generated by the benchmark. The committed product should primarily be the reproducible benchmark mechanism.

The benchmark must be runnable against later trees without changing benchmark logic, so the results from this mission's starting tree can be compared with TASK-2400/TASK-2401/TASK-2402 after they are integrated.

Also measure CLI/module startup sufficiently to answer the specific follow-up question: are the many static command imports in the CLI composition root a material part of cold-start latency? Do NOT implement lazy imports in this mission. Produce evidence that can justify or reject a later mission.

Avoid benchmarks whose dominant cost is building Parallix itself. Build once outside the timed region where the benchmark is intended to measure runtime behavior.

Keep the harness out of normal production hot paths and do not add always-on production telemetry merely to benchmark.
