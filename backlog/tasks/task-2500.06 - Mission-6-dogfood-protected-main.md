## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Base: TASK-2500. Mission 6 of 6. Configure the Parallix GitHub repository to use `github-publish` for its own development and make GitHub `main` an externally verified publication boundary.

DESIRED MODEL:
```text
local main
    = high-speed Parallix integration trunk
origin/main
    = highest contiguous externally verified publication commit
```
Parallix development must not wait synchronously for GitHub CI after every mission.

DEPENDENCY ORDER: base TASK-2500. Depends on Missions 2, 4, 5 (TASK-2500.02, TASK-2500.04, TASK-2500.05). Recommended after Mission 3 (TASK-2500.03) is sufficiently stable to avoid painting the integration model into a corner.
<!-- SECTION:DESCRIPTION:END -->

## Mission Requirements

### Migration requirements BEFORE enabling protection:
1. prove the required GitHub check works;
2. prove a locally created integration commit can be independently verified;
3. prove the exact verified SHA can advance protected `main`;
4. prove local main can remain multiple commits ahead;
5. prove publication catches up without local-history rewriting;
6. prove failed verification blocks publication rather than blocking continued local development.

### Branch protection intent — enable:
- required status check: `ci-required`;
- prevent force pushes;
- prevent deletion;
- evaluate and enable linear history where compatible.

### Do NOT require:
- "Require a pull request before merging" — `github-publish` intentionally publishes locally created commits directly after independent verification.
- a second human approval merely to satisfy a checkbox for the current single-maintainer repository.
- "branch must be up to date" if it destroys speculative local throughput; Parallix's ordered publication rule provides the stronger relevant invariant for this mode.

### Live verification proof (folded from task-2500.05 SC2/SC7)

task-2500.05 built `.github/workflows/ci-required.yml` and closed SC1, SC3,
SC4, SC5, SC6 locally. SC2 (the `ci-required` job runs for the established
`github-publish` verification ref, checking out the event's exact `github.sha`)
and SC7 (one successful live GitHub Actions `ci-required` run recorded with its
run URL / run-id and elapsed time) were deferred there because the concrete
`github-publish` verification ref was unestablished (ADR 0045). This mission
owns that ref, so SC2/SC7 land here:

- Name the exact `github-publish` verification ref (branch / tag / ref) and
  trace it to implementation or parent-mission evidence.
- Confirm/correct the workflow's publication trigger
  (`.github/workflows/ci-required.yml`) to match the established ref; confine
  any edit to that file.
- Trigger the workflow on that ref, run the `ci-required` job on a clean
  `ubuntu-latest` runner, and record the run URL / run-id and elapsed time.
- Close SC2 and SC7.

## Stop Rules
- Stop and ask for direction if the exact `github-publish` verification ref
  cannot be established from implementation or parent-mission evidence.
- Stop and ask for direction if triggering the workflow requires an operator
  action not available in a local-only session: an operator-approved push of
  `.github/workflows/ci-required.yml` to `origin` `main`, or a sanctioned
  verification branch reachable by GitHub Actions. Without that operator action
  SC2/SC7 cannot be completed (local-only policy blocks pushing to `origin`
  `main`; the `review` remote is Forgejo without GitHub Actions).
