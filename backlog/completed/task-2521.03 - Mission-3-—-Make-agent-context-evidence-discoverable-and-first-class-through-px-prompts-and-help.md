## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Part of wave TASK-2521 (read its architectural constraints and mandatory agent-slop checks; they apply here).

Depends on: Mission 2 (TASK-2521.02).

Purpose: replace both sides of the file-based agent protocol. Removing repository workflow files is viable only when agents can obtain all former context and perform every legitimate workflow mutation through supported application operations.

### Architectural rule

The required flow is:

```text
authoritative state + external facts -> application query -> Markdown / JSON context -> agent
agent intent / evidence -> supported px/application command -> domain/application validation -> authoritative state
```

It is neither `agent -> SQL` nor `agent -> generated Markdown file -> parser -> DB`.
Temporary files are permitted only as runner or CLI transport; a durable write must go through the application command.

### First checkpoint: mutation-parity audit

Before adding commands, enumerate every legitimate mutation agents currently perform through repository workflow files. Inspect at least task creation; task title/description/labels/priority changes; assignment; dependencies; refinement; goal/context/scope/constraint changes; predicted NEL/confidence/selection signals; mission gates; activation and lifecycle transitions; checkpoint creation and correction; Goal Check evidence; review findings, resolutions, dispositions and interventions; closeout; follow-up/bug task creation; and every production write found by Mission 1.

Record the mapping as checkpoint evidence or test data, never as a new committed Markdown inventory. Each legacy mutation must map to an existing supported operation, a new operation implemented by this wave, an externally-authoritative provider operation, or an explicitly unsupported operation with an architectural reason. Manual DB/file editing is not a category.

### Domain operations, not storage CRUD

Commands express domain intent, following established `px` conventions: Mission context read; execution-specification update; assignment set/clear; dependency add/remove; refinement update; checkpoint record/replace; review finding/decision record; resolution submit; task create/update/archive; and lifecycle transition. Do not expose generic table CRUD, SQL, or an arbitrary JSON patch endpoint.

Deletion is semantic, not automatic: dependencies, optional constraints, and assignments may be removed where valid; checkpoints are corrected through replacement; review history and closure retain their lifecycle invariants.

### Mission context read surface

Provide a discoverable, application-owned query for humans and agents. It must expose the relevant combination of Mission identity/status/title; goal/why/scope/constraints; refinement signals, predicted NEL and confidence; dependencies and predecessor outcomes; assignment; mission gates; current checkpoint evidence; outstanding findings and prior resolutions; Git/revision observations; verification state where relevant; and external task reference/context.

Support machine-readable output where agents would otherwise parse decorated terminal text. Starting with only a Mission slug and `px --help`, an agent must be able to discover it without repository internals.

### Mission context write surface

Provide non-interactive, validated application requests for every mutable execution field identified by the audit: goal, why/context, scope, constraints, refinement signals, predicted NEL/confidence/selection note, gates, assignment, dependencies, and other bounded Mission 2 fields with current consumers.

Updates must preserve omitted fields, define clearing/removal semantics where supported, reject invalid lifecycle changes and stale writes, and return enough resulting state/version for deterministic re-query. They must not require editing a repository file.

### Checkpoint and review write surfaces

Agents must record real checkpoint evidence without `CP-N.md`: identify Mission and checkpoint, submit Goal Check criterion/evidence rows and next action, validate existing domain rules, reject another Mission's evidence, support same-checkpoint correction/replacement, persist through the Mission boundary, and return/query the result. The harness must not invent semantic evidence.

Agents must likewise use supported review operations for reviewer findings/decisions, implementer resolutions with evidence or rationale, resulting revision, and supported intervention/escalation. Preserve revision, round, and lifecycle invariants. A subsequent agent must immediately re-read new review state from the context surface, not a review-event file.

### Task mutations (re-scoped)

The Mission aggregate is the only task record (TASK-2521.04 re-scope). Legacy task mutations map to Mission intake and the existing lifecycle commands, or are recorded as unsupported with a reason. No task-source port, provider, table or CLI is defined. Mission-to-Mission dependency references belong to TASK-2521.04.

### Discoverability, prompts, and structured I/O

`px --help` and relevant command help must make read and write paths discoverable: context, execution-context updates, checkpoint evidence, review submissions, task operations, and lifecycle transitions. Help and runtime prompts must not tell agents to edit `MISSION.md`, CP files, Backlog Markdown, review-event files, or SQLite.

Implementer prompts must use the read surface and mutation commands; reviewer prompts must explain review reads/writes and prior-resolution retrieval; refinement prompts must explain execution-context, dependency, refinement, and follow-up task operations. Prefer JSON request/result forms, stdin, typed flags, or existing CLI conventions over fragile quoting. A temporary input file, if supported for large payloads, is transport only and is never committed.

### Concurrency, verification, and guardrails

Preserve established expected-version/stale-write protection. At minimum prove that agent A reading version N cannot overwrite agent B's version N+1 change; A receives an explicit conflict, can re-query, and retries deliberately.

Do not add `px db set`, `px sql`, generic patch-anything, Markdown/blob authority, a second Mission model, new lifecycle states for convenience, silent evidence generation/clearing, committed request files, generated command inventories, or happy-path-only coverage. If the audit finds a legitimate operation that requires a new architectural concept, stop for architectural review.
