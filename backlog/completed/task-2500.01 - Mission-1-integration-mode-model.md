## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Base: TASK-2500. This is the discovery and design checkpoint for the wave, not the implementation of the integration modes. Audit the current integration path, repository configuration, persisted mission state, review flow, GitHub/Forgejo assumptions, and the documents that describe them. Produce a short, evidence-backed design inventory that lets Missions 2–6 implement the intended model without carrying forward contradictory assumptions.

The design must serve two separate use cases:

- **Parallix developing Parallix:** GitHub makes the configured controls visible and independently verifies the commit that reaches protected `main`. This is `github-publish`: Parallix may integrate locally and continue developing while GitHub verification delays publication only. A human-approval requirement is not part of this use case.
- **An engineer working in a team:** Parallix prepares and submits a reviewable change, but other humans inspect and approve it before GitHub merges it. This is `github-pr`: GitHub owns the final merge and its policy, including any required human approval. Parallix must not report the mission complete from a local merge or an agent review alone.

`local` remains the default, GitHub-unaware mode. It needs no GitHub credential, network connection, or remote policy.

The inventory must distinguish three authorities: Parallix's local mission/review/gate workflow; GitHub's observed check and merge evidence; and a repository team's human review policy. Agent review remains useful evidence, but cannot stand in for a required human approval in the collaborative use case.

Review the existing documentation and ADRs as part of the audit. In particular, identify statements that assume Forgejo is only a viewer or that local squash-merge is the sole completion path, and specify the smallest later documentation/ADR update needed. Do not change runtime code, configuration, tests, or live documentation in this mission.

DEPENDENCY ORDER: this outcome is the shared design input for Missions 2 (`github-publish`) and 3 (`github-pr`). Mission 4 may proceed independently on the GitHub-safe verification tier.
<!-- SECTION:DESCRIPTION:END -->

## Mission Requirements

- Trace every current path by which `px integrate` prepares gates, merges a mission branch, observes review-provider state, records completion, and updates the local primary or recorded feature base.
- Audit configuration and persisted-state seams that later work can use for an explicit `local`, `github-publish`, or `github-pr` mode. Record the compatibility rule: omitted mode means `local`; invalid mode must later fail closed.
- Map the authority and evidence boundary for each mode: who runs local gates, what GitHub independently verifies, who may merge, and what fresh external evidence permits mission closure.
- For `github-publish`, define the exact-commit and ordered-publication boundary needed for GitHub-visible control evidence without making GitHub latency block later local development.
- For `github-pr`, define the handoff boundary from Parallix to GitHub and how repository policy can require approval by another human. Do not prescribe human approval for `github-publish` merely because Parallix is dogfooding itself.
- Identify the smallest integration-mode dispatch/capability boundary needed by later missions; do not implement it here.
- Produce an ADR/documentation impact list covering at least ADR 0045, ADR 0041 where its gate authority is affected, the ADR index, `docs/use-cases.md`, and any user-facing statement that would become false or incomplete. Each entry must say whether it needs amendment, replacement, or no change, and why.

## Acceptance Criteria

- [ ] #3 The `github-publish` design states how GitHub visibly verifies the exact candidate before protected-branch publication, while local development continues.
