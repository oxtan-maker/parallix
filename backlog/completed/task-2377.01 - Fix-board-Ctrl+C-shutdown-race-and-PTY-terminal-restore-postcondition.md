## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
SC20 (`Ctrl+C terminates a real idle px board`) is flaky with `ENOENT: .../stty-after`. Verified root cause, in two parts:

**Part 1 — board side.** Ink v6 enables PTY raw mode in a `useEffect` after the first frame paints. The test polls for the rendered top bar (25ms tick) and immediately sends Ctrl+C. If the byte lands before raw mode is active, the pty line discipline converts it to SIGINT delivered to the PTY session's foreground process group. The outer harness shell runs without job control, so it shares that group with the board process. The board registers **no SIGINT handler anywhere** (not in the TUI source, not in the built bundle, not in Ink), so the process dies by signal (WIFSIGNALED).

**Part 2 — harness side.** When the board dies by SIGINT, the outer shell (which also received the signal while waiting for the foreground child) exits via WCE without running its post-conditions, so `stty-after` is never written and the terminal-restore assertion fails with ENOENT. The postcondition file is written by a shell that shares the Ctrl+C blast radius — structurally unreliable. Additionally, `script` (util-linux) uses `$SHELL` for its outer shell, and dash exits on this even when the child handles the signal cleanly, so the outcome is machine-dependent.

Fixes (both required):

1. **Board**: register a SIGINT handler that performs the same clean exit as the Ctrl+C key path (Ink app exit, which unmounts and restores raw mode). This is also a real user fix: Ctrl+C during board startup currently hard-kills the process with no cleanup.
2. **Harness** (`test/helpers/pty-smoke-harness.ts`): capture the after-state terminal settings from the **test process** — it already opens the tty device fd for `runStty` — after `waitForExit`, and compare against the pre-launch capture. The outer shell keeps writing nothing that a signal can skip; no postcondition depends on a process inside the signal blast radius.
