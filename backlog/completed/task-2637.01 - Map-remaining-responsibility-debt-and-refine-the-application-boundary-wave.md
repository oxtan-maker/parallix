### CP-2 precedent and structural invariant (2026-10-03)

`integrate.ts` and `handoff.ts` establish the usable precedent.  Each adapter
constructs a named, operation-specific port bundle from concrete mechanisms;
composition supplies mission-scoped collaborators; one application use case
decides phase order, branches, retries, lifecycle writes and recovery.  The
adapter may retain stable exported functions that simply delegate so current
callers and tests remain compatible.  `create-cli.ts` may assemble the graph,
but must not decide the next workflow step.

**Proposed invariant — workflow decisions cross an application use-case
boundary.** A production block is application-owned when it decides the next
product-workflow action from workflow state or an integration result (including
lifecycle transition, gate/review/agent retry, recovery, or provider-mode
branch), then invokes or directs another independently supplied capability.
Such decisions must be in an application use case that receives typed,
operation-specific ports. An adapter may (a) implement one external mechanism,
(b) translate a request or render a result, or (c) construct and pass a named
port bundle to one application entry point, but may not retain that decision
loop. Composition may instantiate the bundle but may not run it.

| Case | Classification under the invariant | Why this is deterministic rather than fan-out |
| --- | --- | --- |
| `createHandoffPorts()` / `HandoffCommandUseCase.performHandoff()` and `createIntegratePorts()` / `createIntegrateWorkflow(...).integrate()` | Legitimate adapter binding followed by application sequencing. | The adapter's many imports are implementations of a declared one-operation port; it has no branch selecting the next product phase. The use case owns that control flow. |
| Git, SQLite, Forgejo, filesystem or verification adapter calling several sibling helpers to perform one host operation | Legitimate concrete mechanism. | It selects *how* its one external operation executes, not whether the product now launches an agent, changes lifecycle phase, retries a review, or lands a mission. This directly rejects the retired sibling-import count false positive. |
| CLI/interface parsing flags and rendering a returned outcome | Legitimate request translation/presentation. | It neither constructs a workflow policy nor owns persistence/retry/lifecycle authority. |
| `review-loop.ts` choosing rebase/gate/agent launch/poll/artifact rebound/transition from round state | Forbidden adapter-owned workflow sequencing; move the decision loop to a review application use case. | Its control flow selects successive product actions across typed provider, persistence, gate, rebase and agent capabilities; the ownership follows those decisions, not its number of imports. |
| `active.ts` choosing transition, launch, checkpoint, handoff and review from execution outcome | Forbidden adapter-owned workflow sequencing; extend `ExecuteMissionService`/a typed active workflow use case. | It owns the active lifecycle progression across multiple independently supplied capabilities. |
| `review-commands.ts` choosing durable intervention repair and approval/submission ordering | Forbidden adapter-owned workflow sequencing; extend `ReviewCommandUseCase` with a narrow workflow port. | Provider calls stay adapters, but state-dependent decision and durable ordering cross the use-case boundary. |

The guard should be introduced only after the listed loops have moved, and must
be scoped to the command/review workflow boundary rather than every adapter. A
deterministic executable form is: each workflow-facing adapter has one explicit
application entry and may bind typed ports; it cannot itself import/use the
lifecycle transition, agent-launch, review-round/recovery or phase-gate
workflow operations to choose a follow-on workflow action. Existing canonical
layer and named-package guards remain prerequisite checks, not substitutes.

Limits and false-positive assessment: source imports alone cannot prove a
semantic decision, and a host mechanism can legitimately fan out to many
siblings. The proposed check therefore asserts the explicit boundary and
prohibits only workflow-control collaborators at that boundary; it does not
count imports, infer ownership from filenames, prohibit concrete sibling
mechanism dependencies, or require ports around pure functions. A false
positive is possible where a command adapter temporarily has real workflow
control during staged migration; that is intentional migration debt to remove,
not an allowlist candidate. A semantic ambiguity about retry-budget authority
for `review-artifacts.ts` remains a prerequisite for moving its rebound policy.
