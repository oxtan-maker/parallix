## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`test/unit/repository/file-size-cap.test.ts` lists 27 production files as exceptions to the 500-line cap. The largest at review time are `src/adapters/review/review-commands.ts` (~1,750), `src/application/handoff-command-use-case.ts` (~1,630), `src/interfaces/web/transport.ts` (~1,320), `src/adapters/review/review-artifacts.ts` (~1,150), `src/adapters/backlog/legacy-mission-import.ts` (~1,130), `src/adapters/agents/agents.ts` (~1,110), and `src/adapters/forgejo/forgejo-pr.ts` (~1,090). `src/composition/create-cli.ts` is exactly 1,000 lines. A size guard with this many exceptions reads to reviewers as aspiration rather than enforcement.

The outcome is that the five largest exceptions come off the list through refactors a senior reviewer would accept: each extracted unit has one clear responsibility and a name that describes it, and there are no mechanical part-1/part-2 splits. Evaluate whether `legacy-mission-import.ts` is still needed at all; deleting dead migration code is a valid way to pay down the debt.

Depends on the type-restoration subtasks so refactoring happens on type-checked code.
