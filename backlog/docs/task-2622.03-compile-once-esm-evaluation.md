# TASK-2622.03 compile-once ESM evaluation: rejected

Measured 2026-10-01 on Linux (16 CPUs) with Node v24.21.0, tsx 4.20.6, and
Node v26.10.0 for the covered runs. The pre-trial baseline was
[task-2622.02-worker-profile.md](task-2622.02-worker-profile.md), re-measured on
the current tree before the trial.

**Disposition: reject. Do not adopt compile-once ESM test execution now.** The
measured speedup is large. The trial still failed behavior parity in every
executed tier, and it failed the coverage contract. The parity failures are
built into how a compiled tree is laid out, so they are not small defects to fix
during adoption. All trial wiring lived in a gitignored scratch directory and
has been deleted. No compiled tree, second selection authority, or alternative
runner remains in the repository.

## What was tried

Each candidate compiled every tracked TypeScript file under `src`, `test`,
`scripts`, `web`, and `tools` (1,094 files) into one ESM file per source. The
output was unbundled, non-minified, and had linked source maps back to the
original TypeScript. Candidates were limited to existing tooling:

| Candidate | Cold compile | Warm compile | Notes |
|---|---:|---:|---|
| esbuild 0.25.12 (existing dependency) | 395–453 ms, plus about 170 ms to clean and mirror the tree | about 400 ms (no persistent cache) | Leaves the `.ts` import specifiers that two scripts tests use unchanged |
| tsc 5.9.3 `--noCheck`, `rewriteRelativeImportExtensions`, incremental | 12.7–13.8 s | 3.7–4.6 s | Same runtime behaviour as esbuild; compile cost removes most of the benefit |

These were not candidates. Node's native type stripping is a load-time
transform, not compile-once, and it cannot resolve the repository's `.js`
specifiers for `.ts` sources. Bundlers violate the unbundled requirement.

The runner reused the existing `buildTestRunPlan` argv and membership unchanged.
It made only these changes: removed the tsx `--import`, pointed the bootstrap and
test paths at their compiled `.js` files, added `--enable-source-maps`, and added
a junit reporter for per-case comparison. The trial first set the working
directory to the original checkout. That broke tests that compare
`import.meta.dirname` with `process.cwd()`. The trial therefore copied the
tracked sources into a mirrored root next to their compiled output, symlinked
every other top-level entry, and used that root as both `cwd` and
`PARALLIX_EXECUTION_ROOT`.

## Measured benefit

Paired worker probes used medians of 7 samples. Each row lists tsx, then
esbuild, then tsc. All times are in milliseconds.

| Probe | tsx | esbuild | tsc |
|---|---:|---:|---:|
| Empty worker | 223.0 | 22.2 | 24.0 |
| Test bootstrap | 304.9 | 88.1 | 90.1 |
| Bootstrap + `application-services` import | 578.5 | 181.1 | 182.5 |
| Bootstrap + module-mock re-link | 319.6 | 94.0 | 94.4 |
| Covered empty worker (Node 26.10) | 487.1 | 200.1 | 206.0 |

Suite totals include compilation, execution, LCOV post-processing and cleanup.
The esbuild column includes its compile step. Each population is the tier's
complete file set from the existing selection authority.

| Population | tsx wall / CPU | esbuild wall / CPU |
|---|---:|---:|
| 86 mock-heavy and broad-composition unit files, uncovered | 9.8 s / 48.5 s | 5.2 s / 22.5 s |
| Same 86 files, covered | 17.2 s / 61.1 s | 9.8–11.2 s / 28.0–30.0 s |
| Unit tier (408 files), uncovered | 43.3 s / 220.0 s | 20.9 s / 100.9 s |
| Unit tier (408 files), covered | 60.6 s / 257.7 s | 34.5 s / 127.4 s |
| integration-ci (211 files), uncovered | 70.8 s / 288.8 s | 60.8 s / 212.0 s |
| integration-local (9 files), uncovered | 39.3 s / 46.8 s | 39.9 s / 46.4 s |

The saving is roughly 50% of unit-tier CPU and wall time. It is smaller in
integration-ci and absent in integration-local, where subprocesses dominate. We
did not run agent-e2e, which keeps its default skip policy. Its cost is
dominated by agent time.

## Why it is rejected

1. **Generated files are visible to the scans that guard the tree.** Compiled
   `.js` files sit next to the TypeScript sources in the mirrored root. As a
   result, the following checks failed: the dependency-graph and composition-root
   architecture guards, the ESM-only guard, the file-size cap, the test-category
   and default-suite selection checks, and the tracked-tree Sonar check. Making
   them pass would mean teaching the guards and the selection authority to
   ignore generated files. That is the kind of weakening this wave forbids. A
   layout that keeps the generated files outside the tree breaks the
   `import.meta.url` and `process.cwd()` relationship that the tests depend on.
2. **The tree cannot package or build itself.** The npm pack, install, web
   package, persistent-data reinstall and native SEA smoke tests fail when run
   from the mirrored root.
3. **tsx-only module resolution.** Two unit files use extensionless relative
   imports. These resolve only through tsx, so the files do not load.
4. **A latent speed-sensitive defect.** Several tests make re-imports unique by
   appending `Date.now()` to the URL. In one covered run, the faster compiled
   worker made two imports within the same millisecond and reused a module with
   another test's mock. That failure did not recur in solo reruns.
5. **The coverage contract is not met.**
   - With the existing `src/**/*.ts` include, compiled execution reports no
     covered lines, because the filter matches the executed `.js` URL.
   - Adding a `.js` include brings back 360 unloaded generated files, which then
     have to be removed from the denominator.
   - After normalisation, both runs report the same 334 source files. The
     executable denominator falls from 48,419 to 47,573 lines.
   - The comparable unit line rate falls from 70.865% to 69.527%. On common
     lines, 1,198 covered lines are lost and 199 gained.
   - A load-only probe shows the cause. tsx attribution marks uncalled function
     bodies as covered, while source-mapped compiled output reports them as
     unexecuted. Compiled attribution is the stricter one. Adopting it means an
     explicit decision to re-base the coverage semantics of ADR 0062. It cannot
     be adopted silently as a performance change.

Results that did reach parity: 680 of 680 cases in the mock-heavy and
broad-composition population matched under both tools, cold and warm. That
covered module-mock facades, re-link and fresh-import identity, the
operator-database guard, and the unit CPU-budget reporter.

## Conditions for revisiting

Revisit only if a proposal shows all of the following:

- The scanning guards and selection authority still see only authored sources,
  with no exclusion rules added to them.
- Module URLs, working-directory relationships and packaging behaviour are
  unchanged.
- The tsx-only imports and time-based cache-busters are fixed independently.
- An explicit coverage-semantics decision accepts stricter function-body
  attribution and records a new comparable baseline.

Item 1 touches verification-guard boundaries. It needs a separate user decision
before any implementation. No architectural change is proposed here.
